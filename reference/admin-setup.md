# Что настроить нам

## 1. Сервер

1. Возьмите `fnkc-ctl-server.tar.gz` из [последнего выпуска](https://github.com/fnkc-stats/positron-remote/releases/latest) (CI публикует его вместе с расширением после каждого изменения `ctl/` в main, с файлом `.sha256`) или соберите сами: `npm ci --prefix ctl && npm --prefix ctl run server-bundle` → `ctl/dist/fnkc-ctl-server.tar.gz`. На сервере установите GitHub CLI. Установщик скачивает корень доверия Sigstore, который затем позволяет серверу проверять клиентские bundles без сети; если у сервера нет доступа к GitHub, при первой установке передайте файл с другого компьютера (`FNKC_TRUSTED_ROOT`, см. [Обновление и откат](operations.md#обновление-и-откат)). Обновлениям доступ к GitHub не нужен. Скопируйте архив на сервер, сверьте контрольную сумму и установите:

   ```bash
   sha256sum -c fnkc-ctl-server.tar.gz.sha256
   gh attestation verify fnkc-ctl-server.tar.gz --repo fnkc-stats/positron-remote   # собран CI этого репозитория из main
   tar xzf fnkc-ctl-server.tar.gz && sudo ./fnkc-ctl-server/install.sh
   ```
2. Настройте `/etc/fnkc-ctl/agent.json` (образец: [ctl/examples/agent.json](../ctl/examples/agent.json)):

   - `allowedImages`: `ghcr.io/fnkc-stats/r-env`;
   - `provenanceRepository` и `provenanceWorkflow`: репозиторий и workflow, которым разрешено публиковать Positron-образы; по умолчанию это `fnkc-stats/positron-remote` и `.github/workflows/positron.yml`;
   - `limits` (память, CPU, процессы на проект), `maxProjectsPerUser`, `maxMemoryPerUser`, `reserveMemory`;
   - `idleMinutes`: 120 (0 — никогда не останавливать);
   - `pullImages`: `true`, только если у сервера есть доступ к реестру.
3. Проверьте настройки: `fnkc-ctl admin check-config` (печатает действующие значения и предупреждает о неизвестных ключах — после каждой правки).
4. Проверьте: `sudo sshd -T -C user=fnkc,host=localhost,addr=127.0.0.1 | grep disableforwarding` → `yes`.

Серверы с `keysDir` проверяют подпись и provenance каждого образа перед запуском и отказывают при отсутствии bundle. Клиент получает bundle через GitHub API, а верхний манифест образа — из реестра (оба кешируются на компьютере по дайджесту) и передаёт их по SSH; сервер проверяет, что sha256 манифеста равен закреплённому дайджесту, и проверяет подпись офлайн (`gh attestation verify` для файла манифеста, без реестра и без учётных данных GitHub) с `/etc/fnkc-ctl/trusted-root.jsonl`. Прошедший проверку дайджест запоминается в `/var/lib/fnkc-ctl/verified` (настройка `verifiedDir`), поэтому следующие запуски этого образа не требуют ни проверки, ни доступа клиента к GitHub; работающий проект переподключается без проверки. Установщик обновляет корень доверия Sigstore раз в неделю (таймер systemd `fnkc-ctl-trust-root.timer`, скрипт `/opt/fnkc-ctl/refresh-trust-root.sh`; при неудачной загрузке остаётся прежний файл). Каждый опубликованный образ CI сразу проверяет так же, как сервер (`npm --prefix ctl run test:provenance -- <образ>`). После обновления клиента/сервера пересоберите старые Positron-слои командой **FNKC Projects: Build Environment** для каждой используемой пары окружение/Positron; dispatch по умолчанию создаёт новый digest и аттестацию. Старые образы без provenance fail closed.

## 2. Gitea

1. Шаблоны: по одному репозиторию на версию R, например `template-r-4.2`, `template-r-4.5`, `template-r-4.6`. В каждом:

   - `container.json`: `{ "image": "ghcr.io/fnkc-stats/r-env@sha256:<дайджест окружения этой серии>" }` — R-окружение (тег `<серия>-env-…`, дайджест в сводке workflow **publish-manifest**), не образ с сервером Positron;
   - `renv.lock`: копия `env/versions/<серия>/renv.lock` из того коммита этого репозитория, из которого собран этот дайджест;
   - `.gitignore` (например `.Rhistory`, `.Rproj.user/`, `renv/library/`);
   - `renv/.gitignore` (`library/`, `local/`, `cellar/`, `lock/`, `python/`, `sandbox/`, `staging/`), иначе в каждом новом проекте `renv/` виден как неотслеживаемый.
2. Когда опубликовано новое окружение серии (новые пакеты, см. [README](../README.md#версия-positron)), обновите в шаблоне `container.json` и `renv.lock` одним коммитом. Новая версия Positron шаблоны не меняет. Существующие проекты при этом не меняются; переводите их по одному коммитом с ревью. Отстал ли шаблон, видно в панели **Environment Images** расширения: у серии написано «template pins an older environment», а кнопка копирования на строке серии копирует закрепление самого нового окружения.

## 3. Пользователи

1. Добавление: `sudo fnkc-ctl admin add-user <имя> <имя>.pub` на сервере; пользователь сам добавляет тот же ключ в Gitea.
2. Отключение: `sudo fnkc-ctl admin remove-user <имя>`; команда сначала проверяет, что вся работа пользователя в Gitea, и иначе отказывает (`--lose-work` — отозвать сразу, без проверки, см. [Отключение пользователей](operations.md#отключение-пользователей)); оставшиеся проекты: `sudo fnkc-ctl admin projects <имя>`, удаление после проверки работы в Gitea: `sudo fnkc-ctl admin remove-project <имя> <проект> --delete`. Кто что запустил на сервере: `sudo fnkc-ctl admin status`.
3. Вывод сервера из работы (замена, списание): сначала все отправляют работу в Gitea, затем отзыв доступа и уборка — [чек-лист](operations.md#вывод-сервера-из-работы).

## 4. Что раздать команде

По доверенному каналу (не тем же каналом, которым может воспользоваться посторонний):

- Заполненный `config.json` по образцу [ctl/examples/config.json](../ctl/examples/config.json): адрес сервера в `hosts` (`fnkc@<сервер>`), `gitRemotes` (`ssh://git@<gitea>:2221/stats`). Хост `local` оставьте, только если люди будут запускать проекты у себя; `decryptionHosts` по умолчанию пустой.
- Отпечатки ключей хостов:
  ```bash
  ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub        # сервер, на самом сервере
  ssh-keyscan -p 2221 <gitea> 2>/dev/null | ssh-keygen -lf -   # Gitea; сверьте с ключом в его конфигурации
  ```
  Если сервер переустановлен или заменён с тем же адресом, его ключ хоста новый: раздайте новый отпечаток так же и предупредите, что ключ сменился. Клиент проверяет ключ строго и откажется подключаться, пока пользователь не заменит запись старого ключа ([порядок замены](operations.md#резервные-копии-и-восстановление-сервера), «Сервер пересобран с тем же адресом»).

**Порядок обновления: сначала сервер, потом клиенты.** Новый сервер работает с клиентами предыдущего выпуска, поэтому сервер можно обновить в любое удобное время, не дожидаясь пользователей. Расширение предлагает пользователям обновление, только когда все серверы из их настроек уже умеют то, что нужно новому выпуску (файл `fnkc-projects-compat.json` выпуска: протокол и возможности). Пока сервер не обновлён, у пользователей ничего не меняется; ручная проверка (**Check for Updates**) называет сервер, который нужно обновить. Номера сборок клиента и сервера совпадать не обязаны. Нужно ли обновлять сервер, сказано в заметках выпуска («Server bundle … changed since …: yes/no»). Откат сервера: `sudo /opt/fnkc-ctl/install.sh --rollback` ([подробнее](operations.md#обновление-и-откат)).

Назовите команде версию Positron из [env/positron.args](../env/positron.args) (сейчас 2026.11.1-4): все ставят её и выключают автоматические обновления (Check Setup).

## 5. Резервные копии

Резервных копий томов нет: вся работа должна быть в Gitea, это единственная точка восстановления; незапушенное может пропасть вместе с сервером, и администратор его не восстанавливает. Скажите это команде. Разовые архивы томов — инструмент оператора на случай аварии (восстановление только для проверки, затем том удаляется) — и восстановление сервера: [operations.md](operations.md#резервные-копии-и-восстановление-сервера).

## Выпуски расширения

После каждого изменения `ctl/` в main workflow [extension.yml](../.github/workflows/extension.yml) собирает, тестирует, подписывает (GitHub Artifact Attestation для `.vsix` и `.tar.gz`) и публикует выпуск `fnkc-projects-v<версия>`: `fnkc-projects.vsix`, `fnkc-ctl-server.tar.gz`, контрольные суммы и `fnkc-projects-compat.json` (что нужно этому выпуску от сервера; то же печатает `fnkc-ctl --version --json`). Версия — `<major.minor из ctl/package.json>.<номер запуска>`, так что каждый выпуск новее предыдущего. Выпускается только новейший коммит main: если, пока шла сборка, в main попал более новый коммит с изменениями расширения, выпуск делает его запуск. «Последним» (его получают обновления расширения) становится только выпуск новее текущего последнего: повторный или запоздавший запуск старого коммита публикует свой выпуск, но не заменяет последний. Выпуск сначала создаётся черновиком (его не видят ни обновления расширения, ни ссылка для первой установки), получает все пять файлов, шаг скачивает их обратно, сверяет с файлами своей сборки и обе контрольные суммы и только после этого публикует выпуск. Если GitHub отказал или файлы не сошлись, шаг повторяет попытку; если и это не помогло, черновик остаётся, а повторный запуск (**Re-run**) загружает файлы заново и публикует его. Черновик запуска, который тем временем вытеснил более новый коммит, удаляется. Установленные расширения раз в день спрашивают последний выпуск (без учётных данных, репозиторий публичный), и, если все серверы из настроек пользователя к нему готовы, предлагают **Update**, сверяют скачанный файл с его `.sha256` и устанавливают его. Если какой-то сервер не ответил, автоматическая проверка повторяется при следующем запуске; ручная предлагает обновление с предупреждением. Отключить проверку: настройка `fnkcProjects.checkForUpdates`. Ссылка для первой установки не меняется: `https://github.com/fnkc-stats/positron-remote/releases/latest/download/fnkc-projects.vsix`. Сервер сам не обновляется: новую версию `fnkc-ctl-server.tar.gz` из того же выпуска администратор ставит, как в шаге 1, когда в заметках выпуска написано «Server bundle … changed …: yes».
