# Выполнение кода агентов и работа с чувствительными данными

ИИ-автору не нужно видеть данные, чтобы написать код, который потом их раскроет. Считайте ревью кода и доступ к результатам частью границы защиты данных. Git-crypt защищает отслеживаемое содержимое репозитория при хранении в Git; расшифрованные рабочие копии, выгрузки, логи и отчёты нужно защищать отдельно.

Используйте три роли выполнения:

| Роль | Код и данные | Учётные данные | Результаты |
| --- | --- | --- | --- |
| Аналитик | Постоянная рабочая копия; явно разрешённые расшифрованные данные | Доступ человека к проекту | Рабочая область под контролем команды |
| Агент, пишущий код / обычные проверки PR | Только одноразовый клон и синтетические тестовые данные | Ограниченный ключ репозитория; без SSH-агента человека | PR и результаты тестов на синтетических данных |
| Проверенный отчёт на реальных данных | Точный согласованный коммит; неизменяемый снимок данных только для чтения | Учётные данные оператора только на хосте; задаче не передаются | Закрытый лог/отчёт, ожидающий проверки результатов |

Workflow PR в Gitea с секретами здесь не включён. Не давайте заданию PR ключ расшифровки и не подключайте ему том проекта аналитика. Проверки на синтетических данных запускайте автоматически.

Для выполнения на реальных данных запускайте `/opt/fnkc-ctl/render-reviewed.py` от root на том Linux-хосте агента, где находится согласованный образ Docker. Скрипт входит в серверный комплект. Команда `fnkc-ctl admin resolve-image` использует конфигурацию этого хоста из `/etc/fnkc-ctl/agent.json`, а для загруженного клиентом образа сверяет его локальный ID с записью агента в `<imageStagingDir>/loaded/`.

У контейнера рендерера нет сокета Docker, сети и capabilities, он работает от пользователя без root, с корневой файловой системой только для чтения и ограничениями памяти, CPU, числа процессов и времени работы. Его одноразовая рабочая область и закрытые результаты всё равно требуют мониторинга места на диске и, где нужно, квот файловой системы.

Оператор создаёт `/etc/fnkc-ctl/approvals` от root, без права записи для учётной записи CI/агента. `/etc/fnkc-ctl/agent.json` должен принадлежать root и содержать точные разрешённые репозитории образов. После ревью **конкретного коммита** запишите согласование, например:

```json
{
  "repository": "/srv/reviewed-mirrors/study.git",
  "commit": "<40-lowercase-hex-commit>",
  "image": "ghcr.io/fnkc-stats/r-env@sha256:<64-lowercase-hex-digest>",
  "data": "/srv/data-snapshots/study/2026-11-17",
  "dataVersion": "<immutable-data-snapshot-id-or-content-manifest-hash>",
  "document": "report.qmd"
}
```

Репозиторий — локальное зеркало, которое ведёт оператор. Каталог данных должен быть неизменяемым снимком, доступным для чтения UID 1000. Расшифруйте или подготовьте его отдельным разрешённым процессом приёма данных; задача не получает ключ git-crypt. Код читает `/data`. Рендерер проверяет, что `container.json` согласованного коммита содержит согласованный дайджест образа, и выгружает код через `git archive`, без учётных данных из `.git`.

Выполните `sudo /opt/fnkc-ctl/render-reviewed.py <approval-id>`. Команда отказывается работать не от root и с согласованиями, которые могут изменять другие пользователи. Каждый запуск получает новую рабочую область. Его логи, артефакты и сведения о происхождении остаются в закрытом каталоге внутри `/var/lib/fnkc-reports`. Скрипт записывает объявленную версию данных, а не заново вычисленную контрольную сумму всех байтов данных: этот идентификатор и неизменяемость должен обеспечить процесс создания снимка. Образ из согласования скрипт запускает только по неизменяемому ID, который выдаёт `fnkc-ctl admin resolve-image` (те же проверки, что для скрипта резервного копирования, см. [Резервные копии](operations.md#резервные-копии-и-восстановление-сервера)); загруженный клиентом образ без записи о загрузке или с перенесённым тегом скрипт отказывается запускать. В артефактах допустимы каталоги и обычные файлы без дополнительных жёстких ссылок. Если обнаружена символическая ссылка или специальный файл, скрипт прерывает обработку до сообщения о готовности. Новый предложенный коммит требует нового согласования после ревью.

Прежде чем открывать отчёт и логи более широкому кругу, проверьте их на непреднамеренное раскрытие данных. Отчёты автоматически не публикуются и не рассылаются. Если позже добавятся уведомления, отправляйте закрытую ссылку на отчёт с аутентификацией. Ограничьте доступ к отчёту той же аудиторией, что и доступ к данным, если проверка результатов явно не разрешила более широкое распространение. Определите правила хранения и очистки закрытых результатов, включая логи неудавшихся заданий.

Ревью должно охватывать чтение файлов, установку пакетов, внешние процессы, код, создающий результаты, и изменения правил защиты данных. Запрет сети не мешает записать чувствительную информацию прямо в отчёт. Поэтому проверка результатов необходима, даже когда ограничения контейнера работают правильно.

То же относится к журналу запросов сервера (`journalctl -t fnkc-ctl`): в нём имена пользователей и проектов, адреса клиентов и тексты ошибок, в которых бывают пути и вывод `git`. Для обращения в поддержку передавайте выдержку `sudo fnkc-ctl admin support-export` без этих сведений; сырой журнал или выдержку с `--identifiers` сначала просмотрите и сократите, как отчёт. Подробнее: [Журнал запросов](operations.md#журнал-запросов).
