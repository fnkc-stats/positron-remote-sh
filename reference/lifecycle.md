# Lifecycle invariants and recovery

This is the contract for control-plane changes. The CLI and extension share the same application layer (`ctl/src/agent.ts`). Capacity policy is in `capacity.ts`, read-only deletion inspection in `removal-inspection.ts`, image ingestion in `image-store.ts`, and kernel locks in `lock.ts`.

## Environment identity

A project pins an immutable environment image. Its `renv.lock` adds the desired R package versions and source provenance. Every ordinary R startup, including Rscript and Quarto, verifies installed versions and `Remote*` provenance. Missing or mismatched packages trigger restoration under a project environment lock. A failed restore exits before analysis and leaves no success marker. Restarting R retries.

Use `renv::install()` for intentional changes, then run `fnkc-projects snapshot` in the terminal **before starting another R session**. Snapshot deliberately observes installed changes instead of restoring over them. It requires a successful restore of the current lockfile, compares full source records (including `RemoteSha`), writes and validates a candidate, and atomically replaces `renv.lock`. Review and commit it. Stopping a container never snapshots or rewrites dependencies. Explicit startup bypasses such as `R --vanilla` remain expert tools, outside this guarantee; containers execute trusted team code.

Runtime state lives under `renv/.fnkc-*`, excluded locally from Git. A kernel lock serializes restore and snapshot. Manual package installation should not run concurrently with analysis, restore, or snapshot. Ordinary Git operations and editor saves do not take this lock. Snapshot serializes and validates the new `renv.lock` first, then checks that the file is unchanged immediately before the rename; restore checks it before writing its success marker. An edit made during snapshot preparation is therefore refused, but a write landing between that last check and the rename can still be lost: the window is narrowed, not closed. Do not check out or edit `renv.lock` while a snapshot runs, and review `git diff renv.lock` before committing.

## Project lifecycle

- **Initializing:** `.fnkc-init/repo` contains an unexposed clone on the project volume. Interrupted cloning can be retried. Once ready, a request record pins its repository/revision and top-level entries move atomically into place. Retry preserves entries already promoted and refuses conflicting destinations. `.fnkc-init-done` is disposable completed staging.
- **Ready/stopped:** the canonical container name is `fnkc-<user>-<project>`. Labels identify its user and project. A project literally named `study-previous` is valid and visible.
- **Replacing:** the old stopped container is renamed to `fnkc.recovery.<user>.<project>`, outside the public namespace. Its immutable ownership labels remain attached. A missing new container causes rollback on retry; an unstarted replacement is discarded without volumes and the old one restored; a running replacement must pass readiness before the old one is removed. A replacement that fails readiness (one created now, or a running one left by an interrupted replacement) is answered with `ReplacementNotReady` (error code `replacement-not-ready`) carrying the tail of its readiness log: the failing checks and the last lines of `docker logs`. The client may then offer Discard and retry (optional capability `discard-replacement-v1`): the start again with `discardReplacement: true` removes a running replacement only if it still fails readiness (never its volumes; a ready one is never discarded) and creates the container afresh. The `fnkc.recovery.<user>.<project>` container is never started, renamed back or removed by the discard: it stays for operators until a start succeeds, which removes it as usual. There is no analyst rollback to it. A second failure after the discard ends the Open: the new environment does not start on this host (ask an administrator, or revert the pin change). Older hosts ignore the field and never send the code; clients send it only to hosts with the capability.
- **Legacy recovery:** `<canonical>-previous` is recognized only when its ownership labels identify the original project. A real suffix-named project is never treated as recovery. Legacy `.fnkc-initializing` clones still require operator inspection because their previous implementation did not record sufficient resumable state.

An existing checkout's manifest/revision takes precedence over remote HEAD, including a staged initialization ready for promotion. Before choosing an image, Open asks the selected host for the checkout (`agent checkout`, optional capability `checkout-query-v1`): the host reads the manifest read-only with an image it already has (the project container's, else its newest environment image), never the proposed one, and waits at most 5 seconds for the project lock. A checkout that pins an environment without a server of this Positron build therefore still opens; the start reads the checkout again under its lock. Remote HEAD (Gitea, else the client's last copy) is read only when no checkout is adopted, so a checkout on the host opens while Gitea is down or while upstream HEAD lacks a valid manifest, even from a fresh client; older hosts and new projects use remote HEAD as before. The client's Git cache moves its last-good ref only after the new commit's `container.json` is read and valid: a lost connection or a fetch timeout keeps the last usable pin and commit, while a HEAD without `container.json` is an error, not an outage. The same query, sent to all other hosts at once with a 10-second limit and Open's Cancel, tells whether the project also runs elsewhere (older hosts are listed instead). Stop by owner/name or URL (`agent stop <project> <repository>`, optional capability `qualified-stop-v1`) compares the repository with the container's `fnkc.repository` label under the project lock: a container of another repository with the same name, or one without the label, is left running and named in the reply. The client sends it only to hosts with the capability; an older host is reported and left alone (it would refuse the extra argument anyway). A plain name stops the project's container as before. The reply's `stopped` (true for a container that is stopped now, also one that already was) stays for older clients; newer hosts add `outcome` (`absent`, `already-stopped`, `stopped`, `other-repository`), which clients derive from `stopped` for older hosts. A Stop on every host reports each host's outcome and fails (exit 1) if a host could not be asked. Clone commands have a 30-minute deadline. A timeout may leave resumable staging, never an instruction to overwrite user work.

## Lock ordering and availability

Project operations acquire `project-<user>-<project>`. Starts hold the host admission lock only while checking running resource budgets and starting the container. Slow pulls, extension setup, stops, cloning, and backups do not hold admission. Image ingestion is serialized by `image-upload`; loading, pulling and image removal share `image-store`. Image operations never acquire project locks. On the client, Open holds a lock per project (two projects open at the same time; a second Open of the same project waits up to two minutes), and downloading an image holds a lock per digest, so two Opens that need the same image download it once. This computer's SSH entries (`~/.ssh/fnkc`) share one lock, `ssh-entries`: Open's name check, entry write and legacy-name cleanup, and Delete's removal of the project's entries, each check that the entry's metadata names exactly that project and host and act on it under the lock, so one project's Delete never removes another project's entry under the same name. The project list's removal of entries whose container is gone and Remove SSH Configuration (all of `~/.ssh/fnkc`) take the same lock: they wait for an Open writing its entry, so the list never removes an entry an Open has just written, and the removal never interleaves with a half-written one. Offboarding (`admin remove-user`) first runs the removal inspection on each of the user's projects, each under its project lock, and refuses while any has work not on Gitea or cannot be inspected (`--lose-work` skips the inspection, so an urgent revocation never waits for it); it then removes the key under the host lock, then stops each running project under its project lock; a start in progress checks the key again under the host lock before admission, so it cannot start a container for a revoked user. Backups use the same project lock as starts, stops and removal; restoring into unrelated names uses a volume lock.

POSIX uses Python 3 `fcntl.flock`; Windows clients use PowerShell named mutexes. Kernel ownership ends on process termination. Persistent `*.kernel` files must **never be deleted** as a recovery action: deleting a locked inode creates a second lock domain. A lost lock helper terminates its owner rather than continuing a mutation without exclusion. Direct Docker operations by administrators bypass this coordination.

## Deletion

Preview fingerprints include deterministic tar content of every durable project volume (including Git objects/refs, untracked and ignored files) and streamed hashes of the stopped container’s changed filesystem paths; the immutable image ID identifies unchanged base files. Deletion recomputes them under the project lock and refuses differences. A failure to read or fingerprint storage prevents deletion. Fingerprinting can take time and read substantial data; deletion is not a constant-time metadata operation.

The report's remote branches are the checkout's last fetched knowledge, not a live guarantee of server retention. Filesystem timestamps alone are normalized in volume fingerprints. Administrators must not mutate or mount a project's storage during preview/deletion. This is concurrency protection for managed operations, not a filesystem snapshot or a backup. Keep independent backups for recovery from intentional deletion.

## Upload and storage bounds

Only one upload stages at a time per host. Additional callers wait up to an hour for their turn and say so ("Waiting for another image upload to this host to finish"); the client keeps the quiet SSH connection alive meanwhile. Reading data or EOF has a 60-second idle deadline and a four-hour overall deadline. Failed uploads clean up staging; the next ingestion removes remnants left by killed upload processes. Digests and architecture are verified before loading.

Defaults in agent configuration:

| Setting | Default | Meaning |
| --- | --- | --- |
| `imageReserve` | `2g` | Free staging space retained beyond declared compressed blobs |
| `maxUnpackedImage` | `64g` | Maximum decompressed layer-stream bytes per uploaded image |
| `maxImageStorage` | `128g` | Conservative sum of Docker image sizes plus incoming unpacked bytes |

The wire format also caps manifests at 4 MiB and compressed images at 32 GiB. Decompression is bounded before Docker extraction. Logical image accounting can double-count shared layers; it intentionally errs toward refusing an upload. These limits are admission policy, not a filesystem quota: unrelated Docker workloads, filesystem overhead and sparse archives require host disk monitoring and a separate Docker data-root capacity/quota policy. Registry pulls are trusted Docker operations and should be provisioned with the same host disk limits.

Digest verification proves content identity. For enrolled server agents (`keysDir` configured), every start also requires a GitHub Artifact Attestation for the runnable image, signed by the configured repository's `.github/workflows/positron.yml` on `refs/heads/main`. Clients download bundles from the GitHub API (inline, or linked and snappy-compressed; with `GH_TOKEN`, `GITHUB_TOKEN` or the `gh` login when there is one, which raises GitHub's limit from 60 requests an hour per address to 5000 per account, sent to `api.github.com` only) and the image's top manifest from the registry, and cache both by digest. The server checks that the manifest's sha256 is the pinned digest and runs `gh attestation verify` on that file with the installed Sigstore trusted root: offline, without the registry or GitHub credentials. It refuses missing or invalid proofs before creating or replacing a container; a running or unchanged existing container needs no proof (connect checks its verified-image mark). Digests that passed are remembered in `verifiedDir` under the signer policy; a policy change verifies again. The trusted root is refreshed weekly by a systemd timer that keeps the previous file when a download fails. `positron.yml` verifies every image this way after attesting it under `staging-<tag>` and before moving the `positron-*` tag to it (`test:provenance`, gh in a container without network; it reuses a published image only when its recipe label `positron.recipe` matches and its attestation verifies, and `positron-promote.yml` moves a tag back to an earlier verified digest), and `ctl-checks.yml` does the same for the template pin's Positron image before every release and pin change (`ctl/test/provenance-pin.sh`), so a change that breaks real verification does not ship. Local-only agents default to no provenance requirement. Existing Positron layers need a fresh **Build Environment** dispatch before they can start under the new policy; it creates a new image digest and attestation. Existing monolithic images with Positron built in must be replaced by a newly attested environment/server image and a reviewed project pin.

## Upgrade and validation

Upgrades go **server first**. A server accepts clients of the previous release: new request fields are optional and new reply fields are ignored by older clients. The server reports its packaged software version, the range of protocol versions it serves (`minProtocol` to `protocol`), and capabilities; clients reject mutations against servers whose range does not include their protocol or that miss the capabilities they require, and build numbers need not match. A change older clients cannot ignore raises the protocol version while the server keeps serving the previous one, so the server can still be upgraded first. Failures carry a `code` (`ctl/src/errors.ts`) that clients act on, so rewording a server message changes no client's behaviour. Each release publishes `fnkc-projects-compat.json` (`fnkc-ctl --version --json`: protocol and required capabilities); the extension offers a release only when every configured server that answers has them, and postpones the automatic offer while a server cannot be asked. Install Python 3 on macOS/Linux clients and the Linux service host.

A running container is never replaced. When a start would set it up differently (new pin, fnkc-ctl assets, key, limits), the host answers with the running container and `updatePending: true`, and the client connects to it as it is and says that the update waits for an explicit stop. A new pin's image that the host does not have is not needed for that: it is asked for (`imageMissing`, the client sends it) only at the first Open after the stop, when the replacement starts. An uploaded tag of the new pin that the host cannot trust is still answered with `imageMissing` at once. The extension's Projects panel then shows that container as "running · update pending" (kept per host and container across reloads) until a listing shows it stopped or gone, or an Open of it comes back without `updatePending`. This requires the container to serve the client's Positron build; otherwise the start is refused with a request to stop and reopen.

Releases: `install.sh` stages each version whole in `/opt/fnkc-ctl/releases/<version>-<checksum>` (all program files and a `MANIFEST` of their checksums), checks it, records the replaced release as `previous-release`, and then switches the single `current` link; the program paths under `/opt/fnkc-ctl` are fixed links through it, so every file changes at once, under an installer lock. Rollback: `sudo /opt/fnkc-ctl/install.sh --rollback` swaps `current` and `previous-release` after a confirmation (a second rollback rolls forward). Both switches write the intended pair of links to `/opt/fnkc-ctl/.release-switch` before changing the two links, and every run first completes (or, if the new release is gone or damaged, undoes) a switch interrupted between them, so the two links never both name one release and neither release is pruned; a `--rollback` that only finished such a switch changes nothing else. Rollback refuses a previous release whose files do not all match its `MANIFEST`. `fnkc-ctl admin status` shows both release IDs, any file that does not match, and a switch still recorded in `.release-switch` (an installer running, or one interrupted; `--json`: `release.pendingSwitch`). Clients that already updated to a release requiring the newer server refuse the rolled-back one until they install the matching older `.vsix` (with `fnkcProjects.checkForUpdates` off). Release notes say whether the server bundle changed since the previous release (its files compared with each build's version number masked).

Release publication depends on `lint.yml` and `ctl-checks.yml`: lint/typecheck/unit tests (the same `./lint.sh` the pre-commit hook runs, including the secret scan), `npm audit` of the build tools, real provenance verification of the template pin's published Positron image, real SSH access and revocation, encrypted backup/restore, clone interruption recovery, noninteractive R restoration and source provenance, and the complete local/server opening workflow. Fixtures use synthetic data and disposable containers. Unit regressions also kill lock owners, stall uploads, exceed decompression budgets, change content without changing Git status, and stop projects during unrelated pulls. Run `./lint.sh` locally; integration commands are listed in that workflow.

## Release history and one-time migrations

These applied once, when moving from an older release; the current rule is the one above (server first, any time).

- **0.3:** the Positron server is part of the image (neither host nor client downloads it), and projects, containers and volumes are named after the Gitea repository. Server and clients were updated together. Containers and volumes made by 0.2 (with a hash in the name) are not used: push the work, stop them and delete them after checking.
- **0.4:** protocol and package rules changed; server and clients were updated together, with old processes ended. macOS/Linux need Python 3. Dependencies are snapshotted explicitly (`fnkc-projects snapshot`); stopping does not change `renv.lock`. Old directory locks are no longer used; leave them alone until old processes have exited. No existing project volumes are renamed. Recovery containers migrate only after their labels prove ownership. Existing R libraries remain on their current volumes.
- **Backup helper check (server bundle after 0.4.146):** `volume-backup.sh` runs its helper only by an image ID that `fnkc-ctl admin resolve-image` verified. Images uploaded by an older fnkc-ctl have no `loaded/<digest>` record, so the script refuses them until each is pulled by digest (host with registry access), untagged and uploaded again by opening a project with it, or recorded with `fnkc-ctl admin record-image` while a project container uses it (bullet «Recording earlier uploads» below; see [operations](operations.md), backups). Projects were not affected until the next bullet.
- **Project images by ID (the server bundle that follows):** project containers are created from the immutable image ID that the same check resolves, never from an uploaded image's tag. An uploaded image without a `loaded/<digest>` record (or whose tag names another image than recorded) is not used: the next Open of a project with it answers `imageMissing`, the client sends the image once more (as for a missing image: no client update, no protocol change), and the host loads it under the tag again and records it. Running containers are not touched, and a project whose container is running reconnects without an upload: an unrecorded tag that still names exactly the running container's image ID is used only to connect to that container as it is (also when an update is pending) and to read its checkout, never to create, replace or start the project's container. The checkout is read with it as `agent checkout` always has: by that container's own image ID, in an unprivileged helper without network that mounts the project volume read-only, so nothing runs that the container does not already run. The re-upload therefore comes at the first Open after the container stops; a container already created from that image keeps its setup (the image ID is the same), so nothing is recreated. A tag moved away from the recorded image is refused even for a running container. Until that container stops, its image still has no record, so `volume-backup.sh` and `render-reviewed.py` refuse it as their helper image: record it with `fnkc-ctl admin record-image` (bullet «Recording earlier uploads» below), or give them a recorded image (for example the template's pin, once a project has been opened with it). On hosts without registry access expect one re-upload per image uploaded before the backup helper check that is not recorded with `admin record-image` first, and one more for any image uploaded while the host was rolled back to a release before it (`install.sh --rollback`), since that release writes no record.
- **Image IDs everywhere (the server bundle after that):** the checkout query and the delete check, when the project has no container, read the volumes only with an environment image whose pin the same check resolves (before: the newest image by name); with none the checkout is `unknown` and Delete is unavailable until a project with an image is opened. A stopped container whose image is not the verified ID is renamed aside and created anew from that ID instead of being started (its setup label alone no longer suffices); running containers are untouched, as always. After `docker load` the host records the image ID only if the tag still names the checked upload: on the classic image store the ID must be the config digest, on the containerd store (Docker 29's default) the image's layers must be the config's diff IDs and its run settings (inspect `.Config`: user, environment, entrypoint, command, working folder, labels, ports, volumes, ...) the config's `config` section; otherwise the upload fails and nothing is recorded. When a pulled `repository@digest` and the uploaded tag of the same digest name different images (normal on the containerd store with `pullImages: true`), the pulled image is used and the uploaded tag is removed with a warning (before: an error); while a container still uses that image Docker refuses the untag, which is only noted (no warning on every Open), and only other untag failures warn. No protocol change, no client update.
- **Reconnect before upload (the server bundle after that):** a running project whose pin moved to an image the host does not have reconnects with `updatePending` instead of answering `imageMissing` (before: the client uploaded the image although the container kept running as it was); the checkout is then read with the running container's own image. The upload comes at the first Open after the stop. No protocol change, no client update.
- **Damaged upload records (the server bundle after that):** a `loaded/<digest>` record that names no image ID (damaged or edited) is refused like a moved tag, also for a running container that uses the image (before: taken for a missing record, so a running container reconnected): the Open answers `imageMissing`, and the upload loads the image under the tag again and rewrites the record; `fnkc-ctl admin resolve-image` names the damaged record. Running containers are not touched. No protocol change, no client update.
- **Recording earlier uploads (the server bundle after that):** `sudo fnkc-ctl admin record-image <repository@sha256:...>` (root only) writes the missing `loaded/<digest>` record of an image uploaded before the backup helper check, so that projects, `volume-backup.sh` and `render-reviewed.py` use it without a new upload. The digest of such an image cannot be checked again (the upload's manifest is gone and `docker load` keeps no digest), so the evidence is a project container fnkc-ctl itself created for it after checking the upload: an fnkc-managed project container pinned to that digest (`FNKC_IMAGE_DIGEST`), created from the upload tag or that image ID, whose image ID is exactly the one the tag names now. Without such a container, or when any project container pinned to the digest runs another image, nothing is recorded; a damaged record or a moved tag is never overwritten; an image already recorded or pulled needs nothing. The record is written with the service account's user and group IDs (not as root, which would follow any link in that account's folder); the command runs under the image-store lock and is journalled (`admin-record-image`). Run it on each host before the project containers that use such images stop: the running projects whose pin has no record are listed by the command in [operations](operations.md#резервные-копии-и-восстановление-сервера). No protocol change, no client update; running containers are not touched.
- **Restore staging namespace (the server bundle after that):** `volume-backup.sh restore` writes only into a new volume named `fnkc.restore.<name>`, a namespace no project or extensions volume can match (their user part is letters and digits only, so even a user named `restore` cannot); any other target exits 2 before Docker is touched. Open (and `agent checkout`) refuses a project's volume that carries the `fnkc.restore` label before reading or mounting it, whatever its name; unlabelled volumes from older fnkc-ctl open as before. A restore made by an older script under a deleted project's real volume name therefore blocks that project's Open with `refusing volume …: it holds a restored archive` until an administrator inspects and removes it (`docker volume ls --filter label=fnkc.restore` lists all restore volumes, old names included). No protocol change, no client update, running containers untouched.
- **Restore label in the removal check (the server bundle after that):** the removal inspection (Delete's preview and the delete itself, `admin remove-project`, and the pre-revoke check of `admin remove-user`) refuses a project volume that carries the `fnkc.restore` label before any helper mounts it, with the same `refusing volume …: it holds a restored archive` error as Open; such a volume is neither read nor deleted as the project's, and `remove-user` without `--lose-work` reports the project as not checked and does not revoke. No protocol change (the error travels as any other removal-check error), no client update, running containers untouched.
- **Restore volumes in status (the server bundle after that):** `fnkc-ctl admin status` ends with the restore staging volumes (labelled `fnkc.restore` or named `fnkc.restore.<name>`), each with its creation time, age, and snapshot/archive label, so volumes left after a recovery drill show up; they are no longer counted as any project's volumes. `--json` adds `restoreVolumes` (`name`, `source`, `created`, `size` with `--sizes`); existing fields are unchanged. Root-only output, no protocol change, no client update, running containers untouched.
- **Volume backups (server bundle):** upgrade restic on the backup host to 0.17 or newer before the next backup. The script uses `--stdin-from-command` so restic saves a snapshot only after the tar helper succeeds. Older restic versions reject the option before creating a snapshot. Restoring an existing backup still uses `restic dump`.
