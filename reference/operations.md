# Руководство оператора

Серверу нужны Linux/systemd, Docker Engine, Node 22.18+, Python 3, GitHub CLI и права root для установки и подключения пользователей. Доступ к демону Docker и право публиковать образы считайте правами администратора. Контейнеры аналитиков предназначены для доверенного кода команды. Автоматическую обработку чувствительных данных выполняйте на отдельном хосте.

## Установка и настройка

Соберите `npm --prefix ctl run server-bundle`, перенесите полученный `ctl/dist/fnkc-ctl-server.tar.gz`, распакуйте и выполните `sudo ./fnkc-ctl-server/install.sh`. Установщик обновляет программу, создаёт служебную учётную запись и общий каталог блокировок, заменяет старый префикс образов по умолчанию точным репозиторием, заново создаёт управляемые строки authorized_keys, записывает фрагмент конфигурации sshd, запрещающий переадресацию, проверяет его и перезагружает sshd. Нужно стандартное подключение `/etc/ssh/sshd_config.d/*.conf`. Старые SSH-сессии установщик не завершает, и окно обслуживания для обновления не нужно (см. [Обновление и откат](#обновление-и-откат)). После каждой правки `agent.json` выполните `fnkc-ctl admin check-config`: команда (root не нужен) печатает действующие настройки с подставленными значениями по умолчанию и предупреждает о неизвестных ключах — опечатка вроде `"idleMinute"` иначе молча оставляет значение по умолчанию. Синтаксическую ошибку агент находит только при следующем запросе, то есть сразу у всех пользователей; установщик выполняет эту проверку в конце.

Настройте `/etc/fnkc-ctl/agent.json` по образцу `ctl/examples/agent.json`:

- `allowedImages`: точные доверенные репозитории; каждый запрос должен содержать дайджест SHA-256. Защитите право записи в эти репозитории.
- `limits`: положительные ограничения памяти и CPU плюс ограничение числа процессов. Ограничение 8 ГБ на проект — не резервирование 8 ГБ на уровне ОС; допуск консервативно суммирует заданные ограничения.
- `maxProjectsPerUser`, `maxMemoryPerUser`, `reserveMemory`: бюджеты допуска. `maxProjectsPerUser: 0` временно запрещает запуск проектов (например, на время обслуживания); работающие проекты продолжают работать. При превышении квоты пользователь видит список своих работающих проектов. Работающие контейнеры без ограничения памяти считаются занимающими ресурсы хоста, поэтому прежде чем допускать проекты анализа, уберите посторонние нагрузки без ограничений или ограничьте их.
- `lockDir`: `/var/lib/fnkc-ctl/locks`, общий для запросов службы, администрирования от root и инструментов резервного копирования. Никогда не используйте разные каталоги блокировок с одним и тем же демоном Docker.
- `idleMinutes`: 120 (так в примере конфигурации). Контейнер без окна и без нагрузки останавливается через 2 часа; считающий без окна — через 3 дня после закрытия последнего окна, и за 2 дня до этого Positron пользователя предлагает продлить (подробно: [Правила](policies.md)). `0` — никогда не останавливать. `agent.json`, созданный более ранней установкой, не меняется: поставьте 120 сами. Научите аналитиков запускать долгие задания через `fnkc-projects run`.
- `pullImages`: по умолчанию `false`. Хостам не нужен доступ к реестру: недостающий образ окружения присылает клиент (см. [Образы окружения](#образы-окружения)). Установите `true` там, где реестр доступен: тогда хост сначала пробует `docker pull`, это быстрее; если скачать не удалось, образ всё равно пришлёт клиент.
- `cranMirror`: зеркало CRAN для пакетов, которых нет в образе (`renv::install()` и восстановление `renv.lock` в контейнерах), по умолчанию `https://mirror.truenetwork.ru/CRAN/`. Только https, адрес оканчивается на `/`. Изменение применяется при пересоздании контейнера (остановите проект и откройте снова).
- `extraHosts`: имена, которые известны только DNS VPN этого компьютера, например `{"git-srv.example.ru": "10.0.0.5"}`; передаются контейнерам проектов как `--add-host`. Нужно для хоста `local` на Mac с раздельным DNS VPN: DNS Docker Desktop его не использует, и клонирование из Gitea завершается ошибкой «Could not resolve hostname». Записи применяются при создании контейнера.
- `imageStagingDir`: куда принимаются и где проверяются загруженные образы перед `docker load` (по умолчанию внутри `~/.cache/fnkc-ctl/images` служебной учётной записи). Нужно свободное место для самого большого образа, для `r-env` около 1 ГБ в сжатом виде; после каждой загрузки каталог очищается, остаётся только запись `loaded/<digest>` с ID загруженного образа.
- Сервер Positron — отдельный слой поверх R-окружения (`~/.positron-server/bin/<commit>`, метки `positron.version`, `positron.commit` и `r-env.base`); хост и клиенты его не скачивают. Проект закрепляет окружение, а хост запускает образ с сервером Positron клиента, только если тот собран на закреплённом окружении (`r-env.base`) и для этой сборки Positron; иначе отклоняет до создания контейнера. Закреплённое окружение на хосте не нужно. Настройки `serverUrlTemplate`, `quality` и `serverArchiveDir` больше не используются, их можно удалить из `agent.json`; том `fnkc-server-<arch>` версии 0.2 можно удалить, когда не останется контейнеров 0.2.

Контейнеры проектов запускаются без лишних привилегий Linux: оставлены только `AUDIT_WRITE CHOWN DAC_OVERRIDE FOWNER KILL NET_BIND_SERVICE SETGID SETUID SYS_CHROOT` (sshd и скрипт запуска) и `no-new-privileges`. После обновления fnkc-ctl остановленные контейнеры пересоздаются при следующем открытии (тома сохраняются).

Проверьте действующие настройки командой `sudo sshd -T -C user=fnkc,host=localhost,addr=127.0.0.1`. `disableforwarding` должен быть `yes`. Пользователи добавляются командой `sudo fnkc-ctl admin add-user anna anna.pub`. Передайте проверенные отпечатки ключей хостов шлюза и Gitea по доверенному каналу. Пока эти ключи хостов не признаны доверенными, SSH-операции клиента завершаются ошибкой.

Размещайте хост на файловой системе, где отслеживаются свободное место и inode. Если рост результатов нужно ограничить, настройте квоты на проекты или файловую систему. Ротация логов в контейнерах проектов настроена, но именованные тома, образы окружения, каталог приёма образов и сохранённые среды выполнения IDE всё равно требуют управления местом. Не выполняйте без разбора `docker system prune --volumes`: так можно уничтожить работу пользователей с остановленными проектами. Удаляйте только проверенные ресурсы, у которых есть резервная копия и на которые ничего не ссылается.

## Образы окружения

Проекты закрепляют образы по дайджесту. Всё, что им нужно, включая R-пакеты, есть в образе ([r-packages.md](r-packages.md)), поэтому работающему контейнеру не нужен репозиторий пакетов, а хосту — реестр:

1. Открытие просит хост запустить проект. Если закреплённого образа на хосте нет (и `pullImages` выключен или скачать не удалось), хост отвечает, какой образ нужен и какая у хоста архитектура.
2. Клиент скачивает образ по дайджесту на компьютере пользователя через HTTP API реестра (публичные образы, анонимный токен; Docker на клиенте не нужен). Для мультиархитектурного образа скачивается только архитектура хоста. Блобы проверяются и хранятся в кеше клиента (`images/` в каталоге кеша), поэтому для следующего хоста или повторной попытки они не скачиваются заново.
3. Клиент передаёт манифесты и блобы потоком через шлюз (`agent install-image <image>`). Хост в `imageStagingDir`, не удерживая блокировку хоста, сверяет манифест с закреплённым дайджестом, каждый блоб — с манифестом, а архитектуру — с архитектурой хоста. Только после этого он под отдельной блокировкой образов собирает из проверенных файлов архив для `docker load` и помечает образ тегом `<repository>:sha256-<digest>`. Реестры сохраняют дайджест образа, а `docker load` — нет, поэтому fnkc-ctl, скрипт резервного копирования и рендерер проверенных отчётов используют этот тег для загруженного образа и ссылку на реестр — для скачанного. Какой ID образа получился при загрузке, fnkc-ctl записывает в `imageStagingDir/loaded/<digest>`, если тег после загрузки указывает именно на проверенный образ (на классическом хранилище образов Docker его ID равен дайджесту конфигурации, на хранилище containerd слои образа совпадают с `diff_ids` конфигурации, а параметры запуска, которые показывает `docker image inspect` (`.Config`: пользователь, переменные окружения, `Entrypoint`, `Cmd`, рабочий каталог, метки, порты, тома и другие), — с разделом `config` проверенной конфигурации; иначе загрузка завершается ошибкой и ничего не записывается): по этой записи fnkc-ctl при открытии проекта, скрипт резервного копирования и рендерер проверенных отчётов (последние два — через `fnkc-ctl admin resolve-image`) проверяют, что тег не перенесён на другой образ, и запускают только этот неизменяемый ID, а не тег. Загруженный образ без записи (загружен старой версией fnkc-ctl или вручную), с повреждённой записью (в ней нет ID образа) или с тегом, указывающим на другой образ, не используется: при открытии хост отвечает, что образа нет, клиент присылает его заново, и хост загружает его под тем же тегом и делает запись. Единственное исключение: если контейнер проекта работает и тег без записи указывает ровно на образ этого контейнера, Open подключается к нему как есть, без повторной загрузки, и читает этим образом checkout проекта (как и `agent checkout`: по ID образа этого контейнера, служебным контейнером без сети и без привилегий, том проекта — только для чтения, поэтому ничего сверх того, что уже работает в контейнере, не запускается). Контейнер проекта из такого образа не создаётся, не заменяется и не запускается, поэтому образ присылается при первом открытии после остановки. Тег, перенесённый с записанного образа на другой, и повреждённая запись не принимаются и для работающего контейнера.
4. Открытие повторяет попытку и запускает контейнер. Образ передаётся один раз для каждой пары хоста и дайджеста.

**Доверие.** Дайджест подтверждает содержимое образа, а GitHub Artifact Attestation подтверждает, что runnable Positron-слой построен разрешённым workflow из `main`. Workflow `positron.yml` публикует attestation для конечного multi-architecture digest. Клиент получает bundles по GitHub API и манифест образа из реестра (один раз на дайджест: они кешируются; если на компьютере есть вход `gh` или `GH_TOKEN`, запрос идёт с ним: без входа GitHub разрешает 60 запросов в час с одного адреса, и при общем адресе офиса лимит может кончиться — тогда открытие называет время сброса); сервер проверяет их офлайн с установленным GitHub Sigstore trust root, включая digest, repo, workflow и source branch, до создания контейнера, и запоминает проверенный дайджест (`verifiedDir`). Если GitHub недоступен, уже проверенные на сервере образы и работающие проекты открываются как обычно. Подключённый пользователь может загрузить собственный образ в Docker, но не сможет запустить его без действительного attestation от разрешённого workflow. При `docker pull` и ручном `docker load` импортируйте именно attested digest. Старые образы без provenance отклоняются: для миграции запустите **FNKC Projects: Build Environment** для используемых пар окружение/Positron, дождитесь новой публикации и откройте снова. Новая сборка получает новый digest. Устанавливайте GitHub CLI на сервер; сетевой доступ нужен установщику и еженедельному таймеру `fnkc-ctl-trust-root.timer` для обновления trust root (без сети остаётся прежний файл; вручную: `/opt/fnkc-ctl/refresh-trust-root.sh`) и клиенту для получения bundle, но проверка на сервере выполняется офлайн.

**Какие образы где.** Панель **Environment Images** в расширении (или `fnkc-ctl images`) показывает:

- опубликованные R-окружения по сериям, новые сверху, по одной строке на образ; под каждым — слои с сервером Positron, собранные для него (раскройте строку), и пометка, если для вашей версии Positron слоя ещё нет. «newest» — самое новое окружение серии; серым — окружения, которые не самые новые, не закреплены шаблоном и не используются контейнерами на доступных хостах, и неиспользуемые слои;
- закрепляет ли шаблон Gitea каждой серии (`template-r-<серия>`, настройка `templateRepository`) самое новое окружение. Шаблоны читаются так же, как `container.json` проекта при открытии; если Gitea недоступна, показывается закрепление, прочитанное в прошлый раз;
- образы на каждом хосте (`agent images`): размер на диске, число контейнеров проектов всех пользователей, сделанных из образа, и сколько из них запущено. Имена чужих проектов не передаются, только числа. Хост со старым fnkc-ctl отвечает, что не умеет перечислять образы; открытие проектов на нём работает как прежде.

**Очистка реестра.** `fnkc-ctl images --cleanup` показывает, что можно удалить из реестра, и ничего не удаляет; с `--delete` удаляет (нужен `gh` с правом `delete:packages`: `gh auth refresh -s read:packages,delete:packages`). Под удаление попадают:

- окружения, которые не самые новые в своей серии, не закреплены шаблоном, не используются контейнерами на хостах и созданы не меньше `--older-than` дней назад (по умолчанию 30), вместе со всеми слоями Positron на них;
- слои для версии Positron, которую команда уже не использует (не та, что в `env/positron.args`), старше 60 дней, если их не использует ни один контейнер;
- образы со встроенным сервером (до разделения), если они не используются;
- слои, окружения которых уже нет в реестре.

Каждый образ удаляется вместе с тегами отдельных архитектур. Команда видит только шаблоны и хосты, а не закрепления всех проектов в Gitea: передайте их через `--keep <файл>` (любой текст с дайджестами `sha256:…`, например вывод поиска по `container.json` всех репозиториев). Если какой-то хост, шаблон или реестр не прочитан, `--delete` отказывается. Удалённый слой Positron собирается снова через Build Environment; открытие, которое помнило удалённый слой, само ищет его заново.

Неиспользуемый образ на сервере удаляет администратор: кнопка в строке копирует команду (`sudo docker image rm <id>`); Docker откажет, если образ использует какой-либо контейнер. Образ на этом компьютере удаляется кнопкой в панели (с подтверждением, только если ни один контейнер его не использует).

## Обновление и откат

**Правило: сначала сервер, в любое время, потом клиенты.** Новый сервер работает с клиентами предыдущего выпуска; работающие проекты продолжают работать, а их пересоздание под новую версию ждёт явной остановки (`updatePending`). Нужно ли ставить новый `fnkc-ctl-server.tar.gz`, сказано в заметках выпуска: «Server bundle … changed since …: yes/no».

Обновление — повторный запуск установщика из нового архива (`sudo ./fnkc-ctl-server/install.sh`). Доступ к GitHub для этого не нужен: если загрузить свежий корень доверия Sigstore не удалось, установщик предупреждает и оставляет установленный файл. При первой установке на сервер без доступа к GitHub сделайте файл на компьютере с `gh` (`gh attestation trusted-root > trusted-root.jsonl`), перенесите его и выполните `sudo FNKC_TRUSTED_ROOT=trusted-root.jsonl ./fnkc-ctl-server/install.sh`; так же его можно заменить позже: `sudo /opt/fnkc-ctl/refresh-trust-root.sh --from trusted-root.jsonl`. Возраст корня виден пользователям в **Check Setup** (старше 30 дней — строка сервера красная) и в отказе проверки provenance; состояние таймера: `systemctl status fnkc-ctl-trust-root.service`.

Каждая версия ставится целиком как выпуск: `/opt/fnkc-ctl/releases/<версия>-<контрольная сумма>` со всеми файлами программы и списком их контрольных сумм (`MANIFEST`). Установщик сначала собирает и проверяет новый выпуск рядом с работающим и только потом переключает на него одну ссылку `/opt/fnkc-ctl/current`; файлы `/opt/fnkc-ctl/fnkc-ctl.cjs`, `volume-backup.sh` и остальные — постоянные ссылки через неё, поэтому все файлы меняются разом, и прерванная установка не оставляет смеси версий. Заменённый выпуск записывается в `/opt/fnkc-ctl/previous-release` до переключения; хранятся только эти два выпуска. Ссылки `current` и `previous-release` меняются двумя шагами, поэтому установщик сначала записывает нужную пару в `/opt/fnkc-ctl/.release-switch`: если установку или откат прервали между шагами, следующий запуск `install.sh` (любой, и `--rollback`) сначала доводит переключение до конца (или отменяет его, если новый выпуск пропал или повреждён) и сообщает об этом; `--rollback` после такого восстановления больше ничего не меняет — для отката запустите его ещё раз. Два установщика одновременно не запускаются (блокировка `/opt/fnkc-ctl/.install.lock`). Первая установка этой версии превращает файлы прежней установки в выпуск, а старую папку `/opt/fnkc-ctl/previous` удаляет. Откат: `sudo /opt/fnkc-ctl/install.sh --rollback` показывает установленную и прежнюю версии и спрашивает подтверждение (`--yes` — без вопроса, для скриптов); повторный откат возвращает новую версию. Откат отказывается, если хоть один файл прежнего выпуска отсутствует или не совпадает с его `MANIFEST`, и ничего не меняет. Какие выпуски стоят и совпадают ли их файлы, показывает `sudo fnkc-ctl admin status` (строка `Installed release`). Если есть незавершённое переключение (запись `.release-switch` осталась), там же видна строка `! unfinished release switch` с обеими парами выпусков — куда и откуда переключали (в `--json` — поле `release.pendingSwitch`): значит, установщик работает прямо сейчас или его прервали; следующий запуск `sudo /opt/fnkc-ctl/install.sh` доведёт или отменит переключение. Настройки, пользователи, образы и работающие проекты не меняются. Если установщик меняет `agent.json` (новые обязательные настройки), он сначала пишет новую версию рядом, проверяет её от имени `fnkc` и только потом подменяет файл; прежняя версия остаётся в `/etc/fnkc-ctl/agent.json.prev`. Откат программы этот файл не трогает: при необходимости верните прежние настройки сами (`cp -p /etc/fnkc-ctl/agent.json.prev /etc/fnkc-ctl/agent.json`, затем `fnkc-ctl admin check-config`). Пользователи, чьё расширение уже обновилось и требует нового сервера, увидят это в Check Setup: им нужно поставить предыдущий `.vsix` из [Releases](https://github.com/fnkc-stats/positron-remote/releases) и выключить `fnkcProjects.checkForUpdates` до следующего обновления сервера.

**Проверка после отката.** Номер версии (`fnkc-ctl --version`) не говорит, что откат прошёл и что клиенты с ним работают. Проверьте две вещи:

1. Установленный выпуск: `sudo fnkc-ctl admin status`, строка `Installed release: <версия>-<сумма> (<N> files, all match its manifest); previous: …`. Действующим должен быть прежний выпуск, его файлы — совпадать с его `MANIFEST`, и под строкой не должно быть строк с `!` (`! active release: …`, `! unfinished release switch …`).
2. Совместимость с клиентами: протокол клиента должен входить в диапазон, который объявляет сервер, и все обязательные возможности клиента должны быть у сервера. Откройте **Check Setup** с той версией расширения, что у команды: зелёная строка `Server '<имя>'` (`fnkc@<сервер>: you are '<имя>', fnkc-ctl <версия>`) значит, что сервер её обслуживает; красная `host runs fnkc-ctl <версия> with incompatible protocol/capabilities; upgrade the server before using this client (<версия клиента>)` — что этой версии расширения нужен более новый сервер (тогда предыдущий `.vsix`, см. выше). Без Check Setup то же видно в ответе сервера: `ssh fnkc@<сервер> fnkc-ctl agent ping` (с ключом, добавленным через `admin add-user`) печатает `{"ok":true,"result":{"version":…,"protocol":…,"minProtocol":…,"capabilities":[…],…}}`; сравните с `fnkc-projects-compat.json` выпуска расширения из [Releases](https://github.com/fnkc-stats/positron-remote/releases): его `protocol` должен быть не меньше `minProtocol` и не больше `protocol` сервера, а каждая строка из его `capabilities` — быть в `capabilities` сервера.

**Откат образа с сервером Positron.** Тег `positron-<версия>-<дайджест окружения>` переезжает на новый образ сам, когда `positron.yml` находит, что опубликованный образ собран по другому рецепту (метка `positron.recipe`: `env/positron.Dockerfile` и аргументы сервера) или его provenance не проверяется. Новый образ сначала публикуется под `staging-<тег>`, аттестуется и проверяется так, как его проверит сервер, и только потом тег переносится на него. Open смотрит, куда указывает тег, при каждом открытии (без реестра — прежний выбор), поэтому новый образ получает следующее открытие каждого проекта, а работающие проекты показывают «update pending». Если с новым образом что-то не так:

1. В сводке запуска `positron image`, который заменил образ, найдите строку «Published … replacing `sha256:…`»: это прежний дайджест.
2. Запустите workflow [positron-promote.yml](../.github/workflows/positron-promote.yml) (Actions → Release · Promote Positron → Run workflow, ветка `main`) с входами `tag` (тег целиком) и `digest` (прежний дайджест) или `gh workflow run positron-promote.yml -R fnkc-stats/positron-remote -f tag=<тег> -f digest=sha256:<…>`. Он ничего не собирает: проверяет, что образ — это то же окружение и та же версия Positron для обеих архитектур с действительным attestation, и переносит тег. Сводка называет, куда тег указывал до этого: повторный запуск с тем дайджестом отменяет откат.
3. Откат временный: следующий запуск `positron.yml` для этого тега (любой merge, который запускает `env-image.yml`) снова соберёт образ по рецепту из `main`. Поэтому сразу отмените изменение рецепта в `main`.

Проекты получают прежний образ при следующем открытии (работающие — после остановки, как при любом обновлении).

## Резервные копии и восстановление сервера

**Вся работа аналитиков должна быть в Gitea, без исключений. Gitea — единственная точка восстановления.** Резервных копий томов команда не делает: всё, что не запушено, может пропасть вместе с сервером. Незапушенные файлы администратор не восстанавливает и коллегам не передаёт, рабочую копию из архива к проекту не подключает. Скажите это команде; при удалении проекта fnkc-ctl показывает, что не запушено, и такую работу владелец отправляет в Gitea сам, пока у него есть доступ (`admin remove-user` без `--lose-work` отказывает, пока она есть).

Скрипт `/opt/fnkc-ctl/volume-backup.sh` — инструмент оператора на случай аварии, а не способ вернуть работу пользователю: разовый архив тома в зашифрованный репозиторий restic. Он отказывается копировать том работающего контейнера и берёт ту же блокировку проекта, что и агент:

```bash
/opt/fnkc-ctl/volume-backup.sh backup fnkc-anna-<project>-project <approved-image@sha256:...>
/opt/fnkc-ctl/volume-backup.sh restore <snapshot-id> /fnkc-anna-<project>-project.tar fnkc.restore.anna-<project>-<дата> <approved-image@sha256:...>
```

Путь к архиву показывает `restic ls <snapshot-id>`; целевой том не должен существовать, а его имя должно начинаться с `fnkc.restore.` (иначе скрипт завершается с кодом 2). Для создания копии нужен restic 0.17 или новее на сервере (проверьте `restic version`). При ошибке tar снимок не сохраняется. Более ранние версии restic отклоняют параметр `--stdin-from-command` до создания снимка. Для восстановления этот параметр не нужен.

**Восстановление** — только проверка архива оператором; никто, кроме оператора, тома восстановления не видит:

1. Восстановите архив в новый промежуточный том `fnkc.restore.<имя>` с именем, по которому видно источник, например `fnkc.restore.anna-<project>-<дата>` (команда `restore` выше). Другие имена скрипт не принимает: тома проектов называются `fnkc-<пользователь>-…` и `fnkc-ext-…`, а в имени пользователя только буквы и цифры, так что имя `fnkc.restore.…` не совпадёт ни с одним томом проекта, в том числе у пользователя `restore`. Снимок и архив записаны в метку тома `fnkc.restore`. Том с этой меткой fnkc-ctl не читает и не подключает, даже если его имя совпадает с томом проекта (так могло быть с томом, восстановленным прежней версией скрипта): открытие такого проекта, а также проверка перед удалением («Delete», `admin remove-project`) и проверка работы перед `admin remove-user` завершаются ошибкой `refusing volume …: it holds a restored archive`, пока администратор не осмотрит и не удалит том (`remove-user` без `--lose-work` из-за этого не отзывает ключ: проект числится непроверенным). Тома проектов без меток (от старых версий fnkc-ctl) открываются как прежде.
2. Проверьте его только на чтение, тем же проверенным образом (том подключается с `readonly`, сеть выключена):

   ```bash
   id="$(sudo fnkc-ctl admin resolve-image <approved-image@sha256:...>)"
   sudo docker run --rm --pull never --network none --read-only --tmpfs /tmp -e HOME=/tmp --cap-drop ALL \
     --security-opt no-new-privileges --user analyst \
     --mount type=volume,source=fnkc.restore.anna-<project>-<дата>,target=/restore,readonly \
     --entrypoint sh "$id" -c 'ls -lab /restore
       g() { git -c safe.directory=/restore -c core.fsmonitor= -c core.hooksPath=/dev/null -c log.showSignature=false -C /restore "$@"; }
       g log -1 --format="%H %an %ad"; g status --short | head -50' 2>&1 | cat -v
   ```

   Убедитесь, что это ожидаемый checkout (репозиторий, последний коммит) и архив читается целиком. Содержимое файлов не открывайте и никуда не копируйте.

   Содержимое тома — от аналитика, поэтому команда ему не доверяет. `git` запускается без настроек репозитория, которые выполняют программы (`core.fsmonitor`, хуки, проверка подписи): иначе программа из `.git/config` подделала бы вывод, по которому вы проверяете архив. Весь вывод идёт через `cat -v`, а имена файлов в `ls` экранирует `-b`: управляющие символы в именах файлов и авторов коммитов показываются как `^[`, `\033`, а не исполняются вашим терминалом. Такие символы в выводе — повод для разбора с владельцем, не ошибка команды; а `M-…` и восьмеричные коды вида `\320` — обычно байты русских букв, их так показывают те же ключи. Не убирайте эти ключи и не запускайте `git` или `ls` на томе восстановления без них.
3. Удалите том: `sudo docker volume rm fnkc.restore.anna-<project>-<дата>`. Оставшиеся тома восстановления (и восстановленные прежними версиями скрипта под другими именами) показывает `sudo fnkc-ctl admin status`: в конце, в разделе `Restore staging volumes`, каждый с датой создания и возрастом («3 days ago»), снимком и архивом из метки (в `--json` — поле `restoreVolumes`: `name`, `source`, `created`). Так видны тома, забытые после учебного восстановления; к проектам они там не относятся. То же без возраста: `sudo docker volume ls --filter label=fnkc.restore`.

Образ, которым скрипт читает и пишет том, проверяется строго, потому что ему доступны личные файлы: `fnkc-ctl admin resolve-image <образ@sha256:...>` (его вызывает сам скрипт) проверяет, что репозиторий есть в `allowedImages`, что при `requireProvenance` этот дайджест уже прошёл проверку provenance на этом сервере, и что локальное имя образа указывает на тот образ, который назван дайджестом. Для скачанного образа это ссылка `репозиторий@sha256:...` в Docker; для загруженного клиентом — тег `<repository>:sha256-<digest>`, который должен указывать на тот же ID образа, что fnkc-ctl записал при загрузке (`imageStagingDir/loaded/<digest>`). Скрипт запускает только этот неизменяемый ID (`--pull never`: из реестра он ничего не скачивает). Отказ означает: образа нет на сервере (откройте проект с ним), он не проверен (возьмите образ, с которым здесь открывали проекты), тег перенесён на другой образ (осмотрите его и удалите тег: `docker image rm <тег>`), или загрузка сделана старой версией fnkc-ctl либо вручную и записи нет (если сервер видит реестр, скачайте образ по дайджесту: `docker pull <репозиторий>@sha256:...`; без реестра, это обычный случай при `pullImages: false`, откройте проект с этим образом: такой тег fnkc-ctl не использует, клиент загрузит образ заново, и fnkc-ctl загрузит его под тем же тегом и сделает запись). Если образ есть и скачанным по дайджесту, и под тегом загрузки, но с разными ID (обычно на хранилище образов containerd, по умолчанию в Docker 29, при `pullImages: true`), используется скачанный, а тег загрузки fnkc-ctl при следующем открытии удаляет с предупреждением. Пока этот образ использует какой-нибудь контейнер, Docker не даёт удалить тег: это ожидаемо, fnkc-ctl лишь отмечает это в журнале (без предупреждения) и удалит тег при одном из следующих открытий; предупреждение выводится, только если тег не удалось удалить по другой причине. Повторная загрузка нужна один раз для каждого образа, загруженного до обновления, если не сделать запись заранее командой `sudo fnkc-ctl admin record-image <репозиторий>@sha256:...`. Она записывает ID образа без записи о загрузке, только если на сервере есть контейнер проекта, созданный fnkc-ctl с этим закреплённым образом (`FNKC_IMAGE_DIGEST`, из тега загрузки или по ID образа), и он использует ровно тот образ, на который сейчас указывает тег загрузки: такой контейнер fnkc-ctl создавал только после проверки загрузки по дайджесту. Сам дайджест заново не проверить (манифест загрузки не сохранился, а `docker load` дайджест не хранит), поэтому без такого контейнера, или если какой-то контейнер проекта с этим закреплённым образом использует другой образ, команда ничего не записывает; повреждённую запись и перенесённый тег она не перезаписывает, а для образа с записью или скачанного по дайджесту ничего не делает. Запись делается от имени служебной учётной записи (не от root, чтобы не пройти по ссылке в её каталоге), команда пишется в журнал запросов (`admin-record-image`). Сделайте её, пока контейнеры проектов работают: после их остановки образ загрузится заново при открытии, а до остановки без записи его не примут ни резервное копирование, ни рендерер. Работающие проекты, у закреплённого образа которых нет записи, показывает команда (образ, скачанный по дайджесту, тоже попадёт в список: `record-image` ответит, что запись ему не нужна):

```bash
sudo sh -c 'dir="$(fnkc-ctl admin check-config | python3 -c "import json,sys; print(json.load(sys.stdin)[\"imageStagingDir\"])")"
  docker ps --filter label=fnkc.managed=1 --filter label=fnkc.project --format "{{.Names}}" | while read -r c; do
    pin="$(docker inspect -f "{{range .Config.Env}}{{println .}}{{end}}" "$c" | sed -n "s/^FNKC_IMAGE_DIGEST=//p")"
    [ -n "$pin" ] && [ ! -e "$dir/loaded/${pin##*@sha256:}" ] && echo "$c $pin"
  done'
```

Для каждого показанного образа: `sudo fnkc-ctl admin record-image <образ@sha256:...>`. Если команда отказывает, для резервного копирования и рендерера возьмите образ с записью (например, закреплённый шаблоном, если с ним уже открывали проект). Повреждённая запись (в ней нет ID образа) тоже означает отказ: удалите тег (`docker image rm <тег>`) и откройте проект с этим образом, клиент загрузит его заново. Тот же отказ ожидаем после отката и возврата на новую версию для образа, загруженного в промежутке.

**Потеря сервера.** На новом сервере: установите fnkc-ctl (см. выше), перенесите `/etc/fnkc-ctl/agent.json` (если его копии нет — настройте заново) и добавьте пользователей снова (`fnkc-ctl admin add-user`, их ключи — те же, что в Gitea). Раздайте пользователям новый адрес и отпечаток ключа хоста. Проекты открываются заново из Gitea; образы окружений приходят с первым открытием.

**Сервер пересобран с тем же адресом.** У нового сервера новый ключ хоста, а компьютеры пользователей помнят старый (обычно в `~/.ssh/known_hosts`). Клиент подключается к серверу со строгой проверкой ключа хоста (`StrictHostKeyChecking=yes`), поэтому до замены записи все действия с этим сервером завершаются ошибкой `Host key verification failed.`; **Check Setup** в строке `Server '<имя>'` пишет `this computer does not know the host key of the server '<имя>' yet` и предлагает подключиться в терминале. Замена ключа:

1. Администратор берёт отпечаток на новом сервере (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) и передаёт его команде по доверенному каналу, как при первой раздаче ([Что раздать команде](admin-setup.md#4-что-раздать-команде)), сообщая, что ключ сменился. Неожиданно сменившийся ключ, о котором администратор не сообщал, может означать, что кто-то стоит посередине: в этом случае не подключайтесь и не удаляйте старую запись.
2. Пользователь подключается в терминале: `ssh fnkc@<сервер> fnkc-ctl agent ping` (для порта не 22 — `ssh -p <порт> …`). ssh отказывается с `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`, показывает отпечаток нового ключа и называет старую запись (`Offending … key in <файл>:<строка>`). Сверьте этот отпечаток с полученным от администратора; только при совпадении удалите старую запись: `ssh-keygen -R <сервер>`, для порта не 22 — `ssh-keygen -R "[<сервер>]:<порт>"`, а если ssh назвал не `~/.ssh/known_hosts`, добавьте `-f <файл>`.
3. Снова `ssh fnkc@<сервер> fnkc-ctl agent ping`: ssh спрашивает о новом ключе и показывает его отпечаток; ещё раз сверьте его и ответьте `yes`. Затем **Check Setup**: строка сервера должна стать зелёной.

Ключи контейнеров проектов (`~/.ssh/fnkc/<имя>.known_hosts`) менять не нужно: клиент записывает их заново при каждом открытии проекта.

## Вывод сервера из работы

Плановый вывод сервера (замена, переезд, списание). Рабочие копии с сервера не переносятся: ни на новый сервер, ни коллегам, ни в архив для пользователей. Всё, что должно уцелеть, пользователи отправляют в Gitea сами, пока у них есть доступ; проекты на новом сервере открываются из Gitea (см. [Резервные копии и восстановление сервера](#резервные-копии-и-восстановление-сервера)). `volume-backup.sh` для переноса томов не используйте. Отдельной команды вывода нет: шаги ниже — существующие команды `fnkc-ctl admin` и ручная уборка того, что ставит `install.sh`.

1. **Замена.** Если работа продолжится на другом сервере, сначала подготовьте его: установка (см. [Установка и настройка](#установка-и-настройка)), копия `/etc/fnkc-ctl/agent.json` со старого сервера, `fnkc-ctl admin check-config`, пользователи (`sudo fnkc-ctl admin add-user`, ключи из `/etc/fnkc-ctl/keys/<имя>.pub` старого сервера). Раздайте команде новый `config.json` и отпечаток ключа нового хоста ([Что раздать команде](admin-setup.md#4-что-раздать-команде)).
2. **Объявление.** Назовите команде дату. До неё каждый отправляет в Gitea всю работу со старого сервера (коммиты, изменённые и новые файлы) и останавливает свои проекты. После даты незапушенное пропадёт; администратор его не восстанавливает.
3. **Опись** (только чтение; вывод называет пользователей и проекты, держите его у себя):

   ```bash
   sudo fnkc-ctl admin list-users
   sudo fnkc-ctl admin status --sizes        # проекты всех пользователей, и удалённых тоже: состояние, тома; тома восстановления
   sudo docker ps -a --filter name=fnkc      # в том числе вспомогательные fnkc.read.*, fnkc.ext.*, fnkc.recovery.*
   sudo docker volume ls --filter name=fnkc  # в том числе тома, которых нет в status (ни проекта, ни восстановления)
   sudo docker volume ls --filter label=fnkc.restore  # все тома восстановления, и под старыми именами fnkc-restore-*
   ```
4. **Остановка.** В назначенный день: `sudo fnkc-ctl admin stop-all --all-users` (перечисляет работающие проекты и спрашивает; несохранённое в их сессиях пропадёт).
5. **Проверка и отзыв доступа.** `sudo fnkc-ctl admin remove-user <имя>` для каждого из `admin list-users` (см. [Отключение пользователей](#отключение-пользователей)). Прежде чем удалить ключ, команда проверяет каждый проект пользователя, как `admin remove-project`, и отказывает («not revoked»), если в каком-то есть работа не в Gitea или проект не удалось проверить («is running: stop it first», «a recovery container … exists; reopen the project»); ключ тогда остаётся. Владелец открывает проект на этом сервере, отправляет работу в Gitea и останавливает проект, затем повторите команду; подробно по проекту: `sudo fnkc-ctl admin remove-project <пользователь> <проект>`. С `--lose-work` доступ отзывается сразу, без проверки, а работа не в Gitea пропадает. Проекты уже удалённых пользователей (`admin status`, «removed») проверьте `admin remove-project`: отправить их работу некому, она пропадает. В конце `sudo fnkc-ctl admin list-users` ничего не печатает.
6. **Удаление проектов.** `sudo fnkc-ctl admin remove-project <пользователь> <проект> --delete` для каждого проекта; проект с работой не в Gitea удаляется только с `--lose-work`. Затем повторите опись из шага 3: оставшиеся тома восстановления (`sudo docker volume ls --filter label=fnkc.restore`) удалите (`sudo docker volume rm …`), остальное, что там осталось, осмотрите, прежде чем удалять. Удаляйте и тогда, когда диски будут стёрты: так видно, что на сервере не осталось неучтённых данных. Разовые архивы томов этого сервера в restic (если оператор их делал) после вывода не нужны ни для какого восстановления: удалите их снимки (`restic forget <snapshot-id> --prune`).
7. **Журнал.** Если сводка запросов может понадобиться позже, сохраните обезличенную выдержку: `sudo fnkc-ctl admin support-export --since <дата установки> > fnkc-ctl-support.txt` (см. [Журнал запросов](#журнал-запросов)). Сырой журнал называет пользователей, адреса и проекты: с сервера его не выносите.
8. **Удаление программы** (если хост остаётся для другого). Сценария удаления нет; `install.sh` ставит вот что:

   ```bash
   sudo systemctl disable --now fnkc-ctl-trust-root.timer
   sudo rm -f /etc/systemd/system/fnkc-ctl-trust-root.service /etc/systemd/system/fnkc-ctl-trust-root.timer
   sudo systemctl daemon-reload
   sudo userdel -r fnkc                       # служебная учётная запись (или ваша FNKC_ACCOUNT) и её authorized_keys
   sudo rm -f /etc/ssh/sshd_config.d/00-fnkc-ctl.conf
   sudo sshd -t && (sudo systemctl reload ssh.service || sudo systemctl reload sshd.service)
   sudo rm -rf /opt/fnkc-ctl /etc/fnkc-ctl /var/lib/fnkc-ctl /usr/local/bin/fnkc-ctl
   sudo docker image ls ghcr.io/fnkc-stats/r-env   # образы окружений: удалите docker image rm
   ```

   Если в `agent.json` заданы свои `keysDir`, `imageStagingDir` или `verifiedDir` вне этих папок, удалите и их.
9. **Компьютеры пользователей.** Новый `config.json` без старого хоста (**Import Configuration…** заменяет прежний файл). Запись ключа старого сервера: `ssh-keygen -R <сервер>`. Подключения к проектам на нём лежат в `~/.ssh/fnkc/`: файлы `<имя>.json` с `"host":"<имя хоста из config.json>"` и рядом `<имя>.conf`, `<имя>.known_hosts` можно удалить (найти: `grep -l '"host":"<имя хоста>"' ~/.ssh/fnkc/*.json`).

## Журнал запросов

Все пользователи входят под одной учётной записью `fnkc`, а сообщения агента уходят клиенту. Поэтому каждый запрос агента и каждая команда `admin add-user`/`remove-user` оставляют одну строку в системном журнале с тегом `fnkc-ctl` (через `logger`; успешные с приоритетом info, ошибки warning). Потерянная строка запрос не останавливает, поэтому установщик в конце отправляет от имени `fnkc` пробную строку `command=install-probe` и предупреждает, если `logger` нет или строка не дошла до журнала:

```
journalctl -t fnkc-ctl --since today
journalctl -t fnkc-ctl -p warning          # только ошибки
journalctl -t fnkc-ctl | grep 'user=anna'
```

Строка состоит из полей `ключ=значение`; значения с пробелами взяты в кавычки как строки JSON:

- `user`: пользователь (из forced command его ключа), `from`: адрес клиента (`SSH_CONNECTION`).
- `command`: `ping`, `list`, `images`, `stop`, `checkout`, `remove-check`, `remove`, `start`, `install-image`, `connect` (подключение Positron к контейнеру: строка пишется, когда соединение закрывается, `ms` — его длительность) или `admin-add-user`/`admin-remove-user`.
- `project`; для `start` ещё `revision`, `image` (закреплённое окружение), `positron` (версия Positron клиента), `client` (версия fnkc-ctl клиента; старые клиенты её не передают), `running` (запущенный образ), `created`, `updatePending`; для `install-image` — `image`.
- Для команд администратора: `by` (кто выполнил через sudo), `key` (отпечаток SHA256 ключа, тот же, что sshd пишет в `Accepted publickey for fnkc … SHA256:…`), для `remove-user` — `unverified` (проекты с работой не в Gitea или без проверки), `lostWork` (отзыв с `--lose-work`, без проверки), `stopped` и `failed`.
- `ms`, `result` (`ok` или `error`), `code` (класс ошибки, если он есть: `quota`, `capacity`, `busy`, `image-missing` и т. п.), `error` (текст, который увидел пользователь), `warnings` (предупреждения через ` | `), `ctl` (версия fnkc-ctl на сервере, которая записала строку; в строках старых версий её нет).

По полю `client` видно, все ли перешли на новую версию (пользователь и версия его клиента за две недели):

```
journalctl -t fnkc-ctl --since -14d -o cat | sed -nE 's/^user=([^ ]*) .*command=start .*client=([^ ]*).*/\1 \2/p' | sort -u
```

**Выдержка для обращения в поддержку.** Строки журнала называют пользователя, его адрес, проект, коммит и образ, а текст ошибок и предупреждений может содержать пути и имена (например, вывод `git` при неудачной проверке рабочей копии). Не вставляйте вывод `journalctl` в общий тикет или чат. Вместо него выполните:

```
sudo fnkc-ctl admin support-export                 # за последние сутки
sudo fnkc-ctl admin support-export --since -7d     # время в формате journalctl: today, -7d, "2026-11-20 10:00"
sudo fnkc-ctl admin support-export --json
```

Выдержка начинается с версий fnkc-ctl и Node.js на сервере, а по каждому запросу содержит только время, `command`, `result`, `category` (класс ошибки: `code`, а для строк старых версий — класс по тексту; `other`, если класс неизвестен), `ms`, версии `client`, `positron` и `ctl`, флаги `created`, `updatePending`, `lostWork` и число предупреждений. Пользователи, адреса, проекты, коммиты, образы, отпечатки ключей и тексты сообщений в неё не попадают; неизвестная команда показывается как `other`, а новые поля журнала не попадают, пока их не внесут в список. Строки другого формата пропускаются (их число указано в заголовке). Всё равно просмотрите выдержку перед отправкой: время запросов тоже сведения.

`--identifiers` добавляет все поля строки, в том числе тексты ошибок, — это то же, что сырой журнал. Такую выдержку, как и вывод `journalctl`, перед отправкой просмотрите и уберите из неё имена пользователей и проектов, адреса, пути, коммиты и всё, что выдаёт содержание работы; передавайте её только тем, кому разрешён доступ к этим данным (см. [Работа с данными](data-execution.md)).

Журнал хранится столько, сколько настроено в journald; чтобы он переживал перезагрузку, нужен каталог `/var/log/journal` (`Storage=persistent` в `/etc/systemd/journald.conf`).

## Восстановление после сбоев

- Остановка: `docker stop` от агента ждёт до 90 секунд. Остановка не меняет зависимости: намеренные изменения заранее фиксируются командой `fnkc-projects snapshot`.
- Изменение настроек во время работы: сохраните работу, дождитесь окончания заданий, явно остановите проект и откройте снова. Открытие никогда не навязывает обновление поверх работающего задания.
- Неудачная замена остановленного контейнера: инициализация по возможности возвращает предыдущее имя контейнера; тома проекта никогда не удаляются. Если процесс умер во время замены, старый контейнер остаётся под именем `fnkc.recovery.<user>.<project>` (вне имён проектов, с теми же метками владельца) и следующее открытие само восстанавливает его или завершает замену; контейнеры старых версий с именем `<container>-previous` распознаются, только если их метки принадлежат этому проекту. Если новый контейнер не проходит проверку готовности, аналитик видит конец его журнала и может нажать **Discard and Retry** (`fnkc-ctl open --discard-replacement`): неготовый контейнер удаляется и создаётся заново, а `fnkc.recovery.<user>.<project>` не трогается и остаётся для разбора (`docker inspect`, `docker logs`) до следующего успешного запуска. Вторая неудача приходит к вам: новое окружение не запускается на этом сервере. Не запускайте два контейнера с одним томом рабочей копии.
- Вспомогательные контейнеры: рабочую копию (при открытии и `agent checkout`, до 20 секунд) и тома перед удалением проекта (до 10 минут) агент читает в контейнерах `fnkc.read.<user>.<project>.<id>`, а том расширений Positron проверяет и готовит перед запуском контейнера (открытие нового или остановленного проекта; к работающему контейнеру открытие подключается без них, не трогая его расширения) в контейнерах `fnkc.ext.<user>.<project>.<id>` (проверка до 20 секунд; подготовка, раз на версию Positron, — до 1 минуты на передачу тома пользователю `analyst` и до 5 минут на установку расширений). `<id>` — 12 шестнадцатеричных цифр. Все они без сети, без журнала Docker, без capabilities, с корневой ФС только для чтения и от имени `analyst` (1000); только передача тома идёт от root с capabilities `CHOWN` и `DAC_READ_SEARCH` (вторая нужна, чтобы зайти в закрытые папки `analyst` с файлами root; запускается только `chown -h`) и с профилем seccomp `ext-owner-seccomp.json` из установленного выпуска (`/opt/fnkc-ctl/current/`): это профиль Docker по умолчанию, в котором запрещены `name_to_handle_at` и `open_by_handle_at` (с `DAC_READ_SEARCH` профиль Docker их разрешает, а они открывают любой файл файловой системы хоста). Если файла нет рядом с `fnkc-ctl.cjs` (программу скопировали без выпуска), передача идёт только с `CHOWN`, с предупреждением «ext-owner-seccomp.json is not installed next to fnkc-ctl …»: файлы root в закрытых папках `analyst` остаются чужими; переустановите сервер `install.sh`. Содержимое тома расширений определяет пользователь, поэтому он может сделать так, что передача тома или установка не уложатся в срок (миллионы файлов, FIFO там, где читает командная строка Positron). Тогда открытие не прерывается: в журнал (`journalctl -t fnkc-ctl`, поле предупреждений) и пользователю идёт предупреждение (например «… timed out after 60 s», «… timed out after 300 s; stop the project and open it again to continue» или ошибка установки расширения), контейнер запускается без новой подготовки, а следующее открытие после остановки пробует подготовить том снова. Если том ещё ни разу не был подготовлен, Positron ставит все свои встроенные расширения сам (и те, что в `skipExtensions`); если был, остаётся прежняя подготовка, возможно, частично изменённая прерванной. Открытие прерывают только ошибки проверки тома и ошибка «could not give the extensions volume to the analyst», когда root не смог передать `analyst` сам том (пользователь вызвать их не может; если передача не уложилась в срок, агент проверяет владельца самого тома, `stat -c %u /ext`, и прерывает открытие, если это не 1000: «… timed out after 60 s, and /ext belongs to uid 0»); если её не снимает повторное открытие после остановки, или подготовка не удаётся раз за разом, остановите проект и удалите том расширений: `docker volume rm fnkc-ext-<user>-<project>-<arch>-<первые 12 знаков коммита Positron>` (`docker volume ls -q | grep '^fnkc-ext-<user>-<project>-'`; в нём только расширения, следующее открытие создаёт и готовит его заново). Файлы тома пользователя (`.fnkc-ctl`) читаются, только если это обычные файлы, не больше 4 КиБ. Если работа не уложилась в срок, агент удаляет такой контейнер сам; если агент умер раньше, контейнер удаляет следующая операция этого проекта, которой нужен вспомогательный контейнер (открытие, `agent checkout`, проверка перед удалением). У них метки `fnkc.helper=read|ext`, `fnkc.helper.user` и `fnkc.helper.project` (не `fnkc.user`/`fnkc.project`: те считаются проектами при допуске). Такие контейнеры показывает `docker ps -a --format '{{.Names}}\t{{.Status}}\t{{.RunningFor}}' | grep -E '^fnkc\.(read|ext)\.'`, контейнеры одного проекта — `grep -E '^fnkc\.(read|ext)\.<user>\.<project>\.[0-9a-f]{12}$'` (точки в имени проекта экранируйте). Не используйте `--filter name=fnkc.read.` или префикс: фильтр — регулярное выражение без привязки, и точки совпадут и с контейнером проекта `fnkc-read-<project>` пользователя `read`, а префикс проекта `a` совпадает и с проектом `a.b`. Работающий контейнер может принадлежать открытию или удалению, которое идёт сейчас: удаляйте (`docker rm -f <имя>`) только те, что старше 10 минут.
- Блокировки: файлы `*.kernel` не удаляйте. Ядро автоматически освобождает блокировку при завершении процесса; наличие файла не означает занятость. На macOS/Linux нужен Python 3, на Windows используется именованный mutex. При переходе с версий до 0.4 (однократно) закройте сессии и завершите старые процессы до обновления: см. [Lifecycle invariants](lifecycle.md#release-history-and-one-time-migrations).
- Прерванное первое клонирование: `.fnkc-initializing` не даёт считать частичную копию полной. Сделайте резервную копию тома, проверьте, есть ли там работа пользователя, и только потом сбрасывайте одноразовый частичный клон или восстанавливайте из резервной копии. Непустые рабочие копии автоматически не удаляются.
- Откат образа: замените в манифесте рабочей копии дайджест на предыдущий сохранённый, остановите и откройте проект снова. Откат образа не отменяет изменения в файлах проекта или данных; при необходимости восстанавливайте их отдельно.

## Отключение пользователей

Выполните `sudo fnkc-ctl admin remove-user anna`. Вся работа должна быть в Gitea до отзыва: после него пользователь отправить её уже не может, а больше некому (резервные копии — для оператора, не для передачи работы). Поэтому команда сначала проверяет каждый проект пользователя, как `admin remove-project` (неотправленные коммиты, изменённые и новые файлы, файлы в домашней папке контейнера вне проекта), и перечисляет те, где есть работа не в Gitea или проверка не прошла (работающий проект проверить нельзя: «is running: stop it first»). Если такие есть, команда отказывает («not revoked») и ничего не меняет: попросите пользователя отправить работу в Gitea и остановить проекты (или остановите их сами: `sudo fnkc-ctl admin stop-all anna`) и повторите команду. `--lose-work` отзывает доступ сразу, без проверки (так и при скомпрометированном ключе: отзыв не ждёт чтения томов); работа не в Gitea тогда пропадает, увидеть её можно потом через `admin remove-project`. После проверки команда удаляет ключ пользователя (под общей блокировкой хоста), затем останавливает каждый его работающий контейнер проекта под блокировкой этого проекта: идущее в этот момент открытие либо закончится до остановки, либо откажет при повторной проверке ключа. Проект, открытый между проверкой и отзывом, команда останавливает и называет («opened after the check»): его работу после проверки посмотрите `admin remove-project`. Если какой-то контейнер остановить не удалось, команда перечисляет его и завершается с ошибкой; повторный запуск для уже отозванного пользователя только останавливает, без проверки. Существующие потоки брокера каждые пять секунд перепроверяют подключение пользователя и закрываются при отзыве. Проверьте результат команды: если контейнер остановить не удалось, администратору нужно разобраться дальше. В конце команда перечисляет оставшиеся проекты пользователя и их тома: они хранятся, пока вы не решите. `sudo fnkc-ctl admin projects anna` показывает их и позже. `sudo fnkc-ctl admin remove-project anna <проект> --delete` удаляет проект, только если в нём нет работы не в Gitea; отправить такую работу после отзыва уже некому, поэтому её удаляют только с `--lose-work`. Отзыв доступа не может вернуть данные или ключи, уже скопированные куда-то ещё; при необходимости смените учётные данные затронутых проектов.

Ведите учёт опубликованных дайджестов окружений, разрешённых URL репозиториев, бюджетов хостов и поддерживаемых версий Positron. После изменений шлюза или OpenSSH повторяйте тесты доступа с двумя пользователями.

Подробные гарантии, ограничения хранения и процедура обновления: [Lifecycle invariants](lifecycle.md).
