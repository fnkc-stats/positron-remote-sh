# FNKC Projects

Воспроизводимый анализ на R в отдельных Docker-контейнерах для каждого пользователя и проекта, в первую очередь на управляемом Linux-сервере. Командная строка и расширение Positron используют один и тот же код. Все бинарные файлы, нужные проекту, включая R-пакеты и сервер Positron, один раз собираются в образ, и проект выбирает его неизменяемый дайджест в `container.json`. Хостам не нужен доступ к Posit, CRAN или реестру образов: если образа на хосте нет, он скачивается на компьютере пользователя, передаётся через шлюз и проверяется хостом. Репозиторий клонируется внутри контейнера.

**Обновления: сначала сервер, в любое время, потом клиенты** (расширение предлагает обновление само, когда серверы готовы). Однократные переходы со старых версий (0.2 → 0.3 → 0.4): [история выпусков](docs/lifecycle.md#release-history-and-one-time-migrations).

## Быстрый старт

**Аналитикам** (подробности: [инструкция](docs/workflow.md)):

1. Получите у администратора: адрес сервера и отпечаток его SSH-ключа хоста, адрес Gitea. Отправьте администратору свой **публичный** SSH-ключ (`~/.ssh/id_ed25519.pub`) и добавьте его в свою учётную запись Gitea.
2. Установите Positron той версии, для которой собраны образы ([Версия Positron](#версия-positron)), и установите расширение из [последнего выпуска](https://github.com/fnkc-stats/positron-remote/releases/latest/download/fnkc-projects.vsix): в Positron **Extensions → … → Install from VSIX**. Дальше расширение обновляется само (раз в день предлагает **Update**; вручную: кнопка **Check for Updates** в заголовке панели Projects или **FNKC Projects: Check for Updates**).
3. Получите у администратора файл `config.json` и выполните **FNKC Projects: Import Configuration…** (кнопка есть и на панели Projects): расширение проверит файл и положит его в `~/.config/fnkc-ctl/config.json`, где его читает и командная строка. Пример для администраторов: [ctl/examples/config.json](ctl/examples/config.json).
4. Сверьте ключи хостов с полученными отпечатками, затем выполните `ssh-add` для своего ключа.
5. Выполните **FNKC Projects: Check Setup** из палитры команд и исправьте всё, о чём она сообщит (в том числе выключите автоматические обновления Positron).
6. Выполните **FNKC Projects: Open Project…** и введите имя репозитория, например `thesis` (или `владелец/имя`, или ссылку на репозиторий из Gitea). Первое открытие нового образа на хосте занимает несколько минут, следующие — секунды.
7. Работайте в открывшемся окне. Коммитьте и пушьте как обычно. Закончив, выполните **FNKC Projects: Stop This Project and Close the Window**: остановка сохраняет тома и не меняет зависимости. После намеренной установки пакетов выполните в терминале `fnkc-projects snapshot`, проверьте и закоммитьте `renv.lock` до остановки.

Новый репозиторий проекта создаётся в Gitea из шаблона нужной версии R: в нём уже есть `container.json` и `renv.lock` ([что настроить администраторам](docs/admin-setup.md)).

**Администраторам**: [сборка и установка](#сборка-и-установка) ниже, затем [руководство оператора](docs/operations.md). **Тем, кто ведёт R-окружение**: [изменение командного образа r-env](docs/r-packages.md#изменение-командного-образа-r-env).

## Архитектура

Локальное расширение/CLI определяет репозиторий и точный начальный коммит; с Gitea на компьютер скачиваются только этот коммит без содержимого файлов и `container.json` (частичный fetch), сам репозиторий клонируется внутри контейнера (`git clone` с переадресацией ssh-agent только на время клонирования). Сервер проверяет права пользователя, разрешённый репозиторий и дайджест образа и постоянную рабочую копию. Для существующей рабочей копии окружение выбирает её собственный `container.json`. Открытие никогда не делает слияние и не переключает существующую ветку автоматически.

У учётной записи шлюза SSH **вся переадресация отключена**. Её принудительная команда (forced command) принимает ограниченные по размеру управляющие запросы и `agent connect <project-id>`. Последняя проверяет, что контейнер принадлежит пользователю, и передаёт поток только на SSH-порт этого контейнера. Адрес или порт назначения вызывающий не задаёт. Клиент закрепляет ключ хоста контейнера, полученный через доверенное управляющее соединение. Перед первым использованием проверьте ключ хоста шлюза.

Проект называется так же, как его репозиторий в Gitea: `muhina-PI-2026-1` — это и строка в списке проектов, и контейнер `fnkc-<user>-muhina-PI-2026-1`, и папка `~/muhina-PI-2026-1` в контейнере. Два репозитория с одинаковым именем (в разных организациях) нельзя открыть на одном хосте одновременно: хост отказывает второму, потому что контейнер и рабочая копия с этим именем принадлежат первому. SSH-псевдонимы включают и хост, и имя проекта. Всегда используйте один канонический URL: хост сравнивает его с URL рабочей копии.

У контейнеров отдельные сети Docker, ограничения памяти, CPU и числа процессов, минимальный набор привилегий Linux (`--cap-drop ALL`, возвращены только нужные sshd и скрипту запуска; `no-new-privileges`), ротация логов и именованные тома для рабочей копии и состояния Positron. Расширения разделены по проекту, архитектуре и коммиту Positron. Сервер Positron находится в образе и доступен только для чтения. PID 1 контейнера — `docker-init`: он передаёт `docker stop` скрипту запуска, который останавливает sshd без перезаписи `renv.lock`. Операции каждого проекта имеют отдельную блокировку; короткая общая блокировка защищает проверку ресурсов и запуск. Образы загружаются отдельно. Блокировки освобождаются ядром при завершении процесса.

В контейнерах аналитиков выполняется доверенный код команды. У них есть доступ к сети для Git и анализа. Они не являются границей изоляции для недоверенного кода агентов или CI с чувствительными данными.

## Требования и поддерживаемые конфигурации

- Сервер: Linux, Docker Engine, Node.js **22.18+**, GitHub CLI, Python 3, OpenSSH с подключаемыми фрагментами конфигурации, systemd. Для диагностики простоя и нехватки памяти (OOM) используйте cgroup v2.
- Клиент: Positron, OpenSSH, Git; доступ к GitHub API для получения подписи образа; Python 3 на macOS/Linux (блокировки), PowerShell на Windows. Для командной строки нужен Node.js 22.18+. Для интерфейса установите VSIX расширения.
- Образы: нативные linux/amd64 и linux/arm64. Эмуляция не допускается: запуск R из командной строки не доказывает, что Positron/Ark будет работать надёжно.
- macOS: Colima или Docker Desktop. Выбранный движок используется через явный контекст; Colima — в собственном профиле `fnkc`, который сам останавливается без контейнеров.
- Windows: начальная настройка через x64 WSL2 остаётся экспериментальной до реального пилота. Windows ARM этой настройкой не поддерживается.
- Docker запускается при необходимости; общий демон остаётся работать. Останавливайте его вручную, когда нужно.

## Сборка и установка

```bash
npm ci --prefix ctl
npm --prefix ctl run check
npm --prefix ctl run package
```

Установите `ctl/dist/fnkc-projects.vsix` командой Positron **Install from VSIX**.
Для установки на сервер соберите `npm --prefix ctl run server-bundle`, скопируйте `ctl/dist/fnkc-ctl-server.tar.gz` на сервер, распакуйте и выполните `sudo ./fnkc-ctl-server/install.sh`. Установщик отключает переадресацию на шлюзе, обновляет подключённые ключи, получает GitHub Sigstore trust root для автономной проверки provenance и перезагружает sshd. Работающие проекты при обновлении продолжают работать; откат: `sudo /opt/fnkc-ctl/install.sh --rollback` ([обновление и откат](docs/operations.md#обновление-и-откат)).

Пользователь добавляется командой `sudo fnkc-ctl admin add-user anna /path/to/anna.pub`. У служебной учётной записи есть доступ к Docker; аналитики не получают её оболочку и общую переадресацию. Точные разрешённые репозитории образов и ресурсы задаются в `/etc/fnkc-ctl/agent.json`.

Скопируйте [пример клиентской конфигурации](ctl/examples/config.json) в `~/.config/fnkc-ctl/config.json`. Настройки подключения и учётных данных — личные настройки компьютера; настройки рабочей области репозитория не могут их переопределить. `decryptionHosts` явно перечисляет серверы, на которых можно расшифровывать данные проектов (Docker на этом компьютере разрешён всегда). По умолчанию список пуст. Расшифровка описана в [docs/workflow.md](docs/workflow.md#зашифрованные-данные).

## Окружения проектов

```json
{
  "image": "ghcr.io/fnkc-stats/r-env@sha256:<published-64-hex-digit-manifest-digest>"
}
```

Используйте дайджест из сводки **publish-manifest** workflow образа. Шаблон в репозитории закрепляет уже опубликованный образ amd64; замените его новым проверенным мультиархитектурным дайджестом, когда он появится. Одни теги без дайджеста не принимаются. На сервере разрешаются точные репозитории образов, а не префиксы целой организации.

Сборка сохраняет в `/usr/local/share/r-env` файл `renv.lock`, его контрольную сумму и список установленных пакетов. Она проверяет R и версию каждого зафиксированного пакета (включая рекомендуемые), загружает пространства имён и проверяет Quarto. CI ([image.yml](.github/workflows/image.yml)) нативно собирает обе архитектуры, рендерит синтетический отчёт, запускает [проверки R-окружения](checks/README.md) и интеграционные тесты SSH, всё без сети, и только после этого публикует уникальные теги и общий манифест. Окружение собирается один раз для каждого набора входных данных ([env/inputs.sh](env/inputs.sh): `env/Dockerfile`, копируемые им файлы, `build.args` и `renv.lock` серии). Если они не изменились, CI берёт уже опубликованное окружение ([env/published.sh](env/published.sh)) и ничего нового не публикует; проверки R (отчёт и [проверки R-окружения](checks/README.md)) запускаются на нём, только если изменились `env/`, `checks/` или workflow образов: тот же образ с теми же проверками дал бы тот же результат. Интеграционные тесты SSH запускаются всегда. Новое окружение получает отчёт об уязвимостях HIGH/CRITICAL (Trivy, только для просмотра) в сводке запуска. Запуск pull request, который устарел из-за нового push, отменяется; запуски в main доводятся до конца. Поэтому изменения fnkc-ctl, проверок и workflow не создают новых дайджестов того же окружения, а проверяются на том, что закрепляют проекты. Слой с сервером Positron тоже публикуется один раз для каждой пары окружения и версии. Опубликованные дайджесты сохраняют установленное окружение; репозитории apt не являются историческими снимками, поэтому повторная сборка из исходников позже не обязательно даст те же системные пакеты.

`r-env` собирается для R 4.2, 4.5 и 4.6, по одному образу на серию, из `env/versions/<series>/` (версия R, дайджест базового образа Rocker, снимок CRAN и `renv.lock`); все публикуются в один репозиторий. Чтобы добавить пакеты в серию, выполните `env/lock.sh <series> <package>...`: скрипт добавит их и их зависимости в `renv.lock` серии из её снимка CRAN. Для нового патч-релиза R или новых версий пакетов измените `build.args` серии и выполните `env/lock.sh --update <series>`. Одна серия собирается локально командой `env/build.sh <series>`. Прежде чем менять дайджест в каждом проекте отдельным коммитом с ревью, проверьте новый образ: `checks/run.sh <image>` проверяет, что его пакеты совместимы, и выполняет типовые задачи команды на синтетических данных ([checks/README.md](checks/README.md)). Проект из шаблона Gitea хранит `renv.lock` своей серии; первая консоль R восстанавливает его, беря версии из образа, так что ничего не скачивается. Пакет, нужный только в одном проекте, устанавливается в контейнере через `renv::install()` из зеркала CRAN команды (настройка хоста `cranMirror`, по умолчанию https://mirror.truenetwork.ru/CRAN/) и записывается в `renv.lock` проекта явно командой `fnkc-projects snapshot` в терминале (остановка контейнера `renv.lock` не меняет); он сохраняется в `renv/library` на томе рабочей копии, а кеш renv — на томе `<base>-library`. Полный порядок работы и правила для загрузок из CRAN и renv: [docs/r-packages.md](docs/r-packages.md).

Если на хосте нет образа для открытия (окружения с сервером вашей версии Positron), открытие скачивает его по дайджесту на вашем компьютере и передаёт через шлюз, а хост перед загрузкой сверяет каждый слой с дайджестом — один раз для каждой пары хоста и образа. Передаётся образ целиком, вместе со слоями окружения: `docker load` не принимает образ без слоёв, даже если они уже есть на хосте. Хосты с доступом к реестру могут скачивать образ сами (`pullImages`). См. [руководство оператора](docs/operations.md#образы-окружения).

Метки окружения описывают его содержимое: `r-env.r-series`, `r-env.r-version`, `r-env.tidyverse-version`, `r-env.cran-snapshot`, `r-env.quarto-version` и `r-env.lock-sha256` (контрольная сумма `renv.lock`); у образа с сервером добавлены `positron.version`, `positron.commit` и `r-env.base` (`docker image inspect <образ> --format '{{json .Config.Labels}}'`). Стандартные метки OCI: `org.opencontainers.image.source` (этот репозиторий; связывает пакет в реестре с ним), `.revision` (коммит сборки), `.version` (версия R). В образе также есть git, git-crypt, GnuPG, Quarto (его pandoc доступен как `pandoc`, им пользуется rmarkdown) и zsh — оболочка пользователя по умолчанию.

## Версия Positron

Образов два вида, оба в репозитории `r-env`:

- **R-окружение** серии ([env/Dockerfile](env/Dockerfile)): R, пакеты, инструменты, пользователь `analyst`, sshd — без сервера Positron. Его закрепляет `container.json` проекта (тег `<серия>-env-…`). Сам он не запускается.
- **Окружение с сервером Positron** ([env/positron.Dockerfile](env/positron.Dockerfile)): закреплённое окружение плюс один слой с сервером одной сборки Positron, с меткой `r-env.base` — окружением, на котором он собран. Его запускает контейнер проекта. Тег `positron-<версия>-<дайджест окружения>`: Open выводит его из закреплённого окружения и версии Positron на компьютере, находит в реестре одним запросом, проверяет метки, и хост запускает его, сам проверив, что он собран на закреплённом окружении. Найденный образ запоминается на компьютере, поэтому следующие открытия реестр не нужен.

Поэтому `container.json` зависит только от R-окружения: проект открывается из любой версии Positron, для которой к его окружению добавлен сервер, и ни при смене версии Positron, ни для члена команды с другой версией закрепление менять не нужно. Серверы Positron скачиваются только при сборке (CI), хосты и контейнеры их не скачивают; сервер подходит только к своей сборке Positron, поэтому автоматические обновления Positron выключены (Check Setup предлагает выключить их: `update.mode: none`).

Версия Positron команды записана в [env/positron.args](env/positron.args), сейчас **2026.11.1-4**: CI добавляет её сервер к каждому новому окружению. Переход команды на новую версию:

1. `env/positron.sh` (без аргументов — последний релиз, или `env/positron.sh 2026.11.1-4`) записывает в `env/positron.args` версию, коммит и контрольные суммы серверов для amd64 и arm64.
2. Коммит и pull request; после слияния CI добавит новый сервер к окружениям серий из `env/versions`.
3. Для окружений, на которые закреплены старые проекты, сервер новой версии добавляется по запросу (ниже) — открытие такого проекта само предложит это. `container.json` проектов и шаблонов не меняется.

**Сервер для своей версии Positron.** Если для окружения проекта нет образа с сервером вашей версии, Open сообщит об этом, и расширение предложит **Build Environment** с уже выбранными окружением и версией или сразу **Copy Request** (просьба администратору, без проверки прав); когда сборка закончится (несколько минут: один слой поверх окружения), оно предложит открыть проект. Нужно один раз на окружение и версию Positron. Вручную: команда **FNKC Projects: Build Environment…** (окружение открытого проекта или новейшее окружение серии, затем версия Positron) или `fnkc-ctl build <окружение | серия> --positron 2026.07.1-5` (по умолчанию — версия Positron на этом компьютере). Это запуск workflow [positron.yml](.github/workflows/positron.yml) с входами `base` и `positron`; сервер этой версии закрепляется в самом запуске, R-часть — побитово закреплённое окружение. Нужен `gh`, вошедший в GitHub (`gh auth login`), с правом записи в репозиторий инфраструктуры (запуск workflow; обычно это администраторы). Без него расширение до всех вопросов называет причину (нет `gh`, нет входа или нет права записи) и копирует просьбу для администратора (**Copy Request**). Версию Positron команды (`POSITRON_VERSION` из `env/positron.args` в `main`) показывают Check Setup и сообщение об отсутствующем образе: другая версия на компьютере — не ошибка, проект откроется после сборки для неё или после обновления Positron. Локально: `env/build.sh 4.6` (окружение `r-env:4.6-env` и образ с сервером команды `r-env:4.6`), `POSITRON=2026.07.1-5 env/build.sh 4.6`, или `BASE=<окружение> env/build.sh 4.6`, чтобы только добавить сервер.

Проекты, которые закрепляют образ со встроенным сервером (до разделения), открываются как раньше: только из той версии Positron, для которой он собран. Чтобы они открывались из любой, переведите их на окружение серии (дайджест `<серия>-env-…`).

## Команды

```bash
node ctl/dist/fnkc-ctl.cjs doctor
node ctl/dist/fnkc-ctl.cjs open thesis --host server
node ctl/dist/fnkc-ctl.cjs open git@gitea.example.lan:stats/thesis.git --host server
node ctl/dist/fnkc-ctl.cjs open thesis --host server --unlock
node ctl/dist/fnkc-ctl.cjs list
node ctl/dist/fnkc-ctl.cjs stop thesis --host server
```

Автоматический выбор берёт только первый хост из настроек. Он никогда незаметно не переключается на ноутбук. Чтобы перенести работу, запушьте изменения и укажите хост явно. Stop принимает имя репозитория (как в списке проектов), `владелец/имя` или его ссылку.

Внутри проекта:

```bash
fnkc-projects status
fnkc-projects sync              # только fetch: не делает слияние и не переключает ветки
fnkc-projects run Rscript analysis.R
fnkc-projects run quarto render report.qmd
fnkc-projects snapshot          # записать установленные R-пакеты в renv.lock (только явно: остановка его не меняет)
fnkc-projects unlock key.asc    # расшифровать вручную (обычно это делает Open): ключ GPG импортируется, файл удаляется из папки
fnkc-projects lock              # блокировка git-crypt; расшифрованные результаты проверяйте отдельно
```

Выключение при простое по умолчанию **0 (отключено)** на сервере и клиенте. Если оператор его включит, обёртка `run` удерживает аренду задания даже во время ожидания ввода-вывода. Явная остановка всё равно завершает всю работу в контейнере. Обычное открытие не блокирует снова ранее расшифрованную рабочую копию. Переадресация агента используется только при инициализации; для обычной работы с Git нужен явно ограниченный ключ или осознанная временная SSH-сессия с переадресацией.

Обновление окружения, ключа, конфигурации или fnkc-ctl не заменяет работающий контейнер: открытие подключается к нему как есть и предупреждает, что обновление ждёт остановки. Когда задания закончатся, сохраните работу, явно остановите проект и откройте снова. При замене остановленного контейнера предыдущий сохраняется, пока инициализация нового не завершится успешно; при ошибках тома проекта сохраняются. Файлы вне подключённых каталогов проекта и Positron не сохраняются.

## Проверка

`./lint.sh` выполняет все статические проверки, которые есть в CI: shellcheck, actionlint, hadolint, поиск секретов (gitleaks; при коммите — только в индексируемых изменениях, иначе по всей истории), проверку «только английский вне Markdown», а также typecheck, тесты и сборку fnkc-ctl. Включите его перед каждым коммитом: `./lint.sh --install-hook`. Остальные задания CI запускаются локально теми же скриптами, что вызывает CI: `./ci-local.sh integration` (интеграционные тесты, около 15 минут, нужен Docker), `./ci-local.sh provenance` (настоящая проверка provenance Positron-образа закрепления шаблона; только на Linux; нужны Docker, gh и сеть) и `./ci-local.sh image <серия>` (сборка окружения и все проверки `image.yml` для архитектуры этого компьютера). Только CI проверяет другую архитектуру, публикует образы и выпуски и создаёт аттестации. Недостающие инструменты запускаются из Docker-образов с закреплёнными версиями. Только CI делает то, что требует сети или собранных образов: `npm audit`, отчёт об уязвимостях нового образа (Trivy), интеграционные тесты.

```bash
./lint.sh
npm --prefix ctl run test:ssh   # нужен локальный образ r-env:verified; только одноразовые тестовые данные
# Или укажите в FNKC_TEST_IMAGE другой совместимый локальный образ.
cd ctl && test/e2e.sh [образ]  # сквозная проверка с Docker этого компьютера (по умолчанию — образ шаблона)
```

Тесты покрывают восстановление после сбоев, откат, одновременные открытия, идентичность рабочей копии, выбор ветки и окружения, квоты, а также отказ в доступе и отзыв доступа по SSH. `npm test` проверяет и расширение: на подставном модуле `vscode` (`ctl/test/fake-vscode.ts`) — что его команды и настройки совпадают с `package.json`, и Build Environment от меню до `container.json`.

[`ctl/test/e2e.sh`](ctl/test/e2e.sh) проходит весь путь проекта: вместо Gitea — одноразовый git-сервер в контейнере, вместо сервера команды — одноразовый Linux-контейнер, на который пакет сервера ставится через `install.sh`. Проверяются отказ для другой сборки Positron, открытие на этом компьютере и через шлюз сервера, расшифровка своим ключом GPG, восстановление `renv.lock` из образа, `fnkc-projects lock` и `unlock` с файлом ключа, `admin add-user` и `remove-user`. Скрипт работает с отдельным `HOME`, ваши `~/.ssh`, `~/.gnupg` и `~/.config` не используются, и всё за собой удаляет (`E2E_KEEP=1` оставляет). Сам Positron он не запускает. Рабочий сервер, внешнее хранилище резервных копий, согласования для реальных данных, окно Positron и клиент на Windows ещё требуют приёмочных проверок.

Точные гарантии, переходы состояний, обновление и проверки: [Lifecycle invariants](docs/lifecycle.md).
